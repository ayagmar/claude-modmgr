## Findings (prioritised)

### 1. BLOCKER · §2.1, §1 F2/F3 · The gate toggle is the only mechanism for dev/inline/skills-dir mods, and nothing establishes that modmgr can load before them

**What's wrong.** F2 proves order among `--plugin-dir` folders; F3 proves order among installed plugins. Neither spike tests an installed plugin (modmgr) against an inline, `CLAUDE_CODE_PLUGIN_DIRS`, `~/.claude/skills/*` or `~/.claude/dev-mods/*` module. The judges of `plugin.register` are "the plugins admitted before it" (d.ts 4348), and that holds at reload too ("at load … and at reload", 4343). If the engine loads folder plugins before installed ones, the gate never sees any dev mod, and the load-first fix cannot help because it only reorders `enabledPlugins` (§2.1) — dev mods are not in that map. The toggle row for exactly the mods that have no CLI disable path would then be dead.

**Fix.** Add spike **S7** to M0: an installed gate (isolated `CLAUDE_CONFIG_DIR`) plus one of each: `--plugin-dir`, `CLAUDE_CODE_PLUGIN_DIRS`, a `~/.claude/skills/<x>` with `modules`, and a dev-mods folder. Record which the gate sees. Design the fallback now: if any class loads first, the Installed/Dev row for it says "can't be toggled from here; disable with `--plugin-dir` removal / move the folder" and the gate column is hidden rather than lying. Do not start M2's `gate.ts` until S7 is written up.

### 2. BLOCKER · §4 `$.store` · The persisted store will exceed the 4 MiB cap and then every write (including `disabledGate`) fails

**What's wrong.** `$.store.set` "rejects … a store over 4 MiB of JSON text in all" (3296). The plan persists `catalog: { at, entries }` (1.82 MB today for 3,544 entries and growing ~30 % since the planning session), `detect: Record<string, Kind>` keyed `<id>@<sha>` and "permanent" (3,500 keys ≈ 300 KB), `validate` per `root@version` with full `Capabilities`, `history: Job[] (≤200)`, prefs and a settings backup. That is already past 2 MiB with one catalogue copy; a second marketplace or a few months of growth and the store rejects. Because the gate reads `disabledGate` from the same store, a full store silently breaks the one safety feature. Each `set` also rewrites the whole JSON file, so the detector writing one key per result (400 per run) rewrites ~2 MB 400 times.

**Fix.** Never persist the catalogue: `list --available` costs 1 s and is the cache. Persist only a compact index if at all (`pluginId`, `kind`, `sha`: ≤ 150 KB). Batch detector writes (one `set` per 50 results or at the end). Cap `detect` by LRU to ~5,000 keys, `history` to 50 entries without tails, and store `validate` as counts plus the capability list, not the whole report. Add a `store.ts` guard: compute the serialized size before `set`, evict, and surface "store near limit" in Health. Spike `claude plugin list --data-size modmgr@…` (exists in 2.1.291) for a measurement in M6.

### 3. MAJOR · §2.1, §2.6, §1 F6/F7 · `reload-plugins` reloads modmgr itself, and CLI installs do not activate without it

**What's wrong.** (a) A reload "re-runs `register` in a fresh environment and the previous environment's timers are dropped" (reference §Developing one); `$.clock.every/after` are cancelled (d.ts 3355); a `$.process.spawn` loop is killed when "the module unload[s]" (3453). The job queue in `jobs.ts` is module memory, so the serial queue, the running `claude plugin test` stream, and the update scheduler all vanish at the one `reload-plugins` the plan runs after each toggle batch. (b) `$.command.run` is "queued and run once the session is idle" and "rejects … inside a hook the turn is waiting on" (2999–3003), so a reload requested from a `/mods` subcommand while a turn runs is refused, not deferred. (c) F6 misreads the docs: "Plugin is now active" is the **in-session** `/plugin install` flow (reference §Sharing a mod). A `claude plugin install` run as a child process does not touch the running session; every install, update, enable and disable from modmgr needs a reload.

**Fix.** Queue state lives in `$.state` (survives reload, 3310) with a `reloadPending` flag; `register` re-reads it and resumes. Never run `reload-plugins` while a job is `running`; schedule it as the last job of a batch and mark the UI "applies after reload (auto)". Catch the rejection from `$.command.run` and fall back to the band's `[r reload]` + "restart to apply". Add install to the reload list in §2.3/M4.

### 4. MAJOR · §2.2 · The risk model mislabels common mods and omits the dangerous calls

**What's wrong.** `tool.call` is "high", yet the engine's own examples (`band.tsx`, `tool-call.ts`) hook it to count calls; nearly every mod will be "high", which makes the label useless. The static scan gives `uses.events` as patterns and `uses.calls` as `noun.method` (7481–7491), so "with auth", "rewrites", "may deny" are not observable statically; the table promises distinctions it cannot make. Missing from the model: `$.mcp.call` (uses the engine's MCP credentials, "No permission prompt", 2634), `$.settings.read` (returns "every key … `env` and the helper commands included: nothing is filtered", 3490–3492, i.e. secrets), `$.session.messages` (whole transcript, 2672), `$.session.authorize`, `$.env.get` of arbitrary names (the names *are* listed, 7496–7504, so API-key reads are detectable), `$.prompt.fill`, `classic.*` hooks, `$.ui.ask`, `$.agent.spawn` (listed medium: it starts model turns that cost money).

**Fix.** Show capabilities as facts in two axes: *reach* (machine: process/fs.write/env.set; network: http.fetch/mcp.call; session content: session.messages/settings.read/env.get[names]; model: prompt.*/tool.call/session.append) and *power* (observes / can change / can block — only where knowable). Compute a short "notable" list from **combinations**: reads session or settings **and** reaches the network; runs processes; gates other plugins. Replace the single `risk` with `notable: string[]`, and keep the per-call one-liner explanations.

### 5. MAJOR · §2.5 Conflicts · Not computable from the data available

**What's wrong.** "Both hook `tool.call` for the same tool", "both draw the same `Pane` id", "both draw `AbovePrompt`": `uses.events` has event names only, no matchers (7486), and `$.ui.panes()` lists "this plugin's own open panes … Another plugin's panes are not listed" (2448–2452). Only "both hook event X" is knowable, which is near-universal noise.

**Fix.** Cut to v1.1, or reduce to the two events where overlap is meaningful and cheap to explain: `prompt.compose` and `session.append` (both rewrite what the model reads, in chain order). Say "in chain order: A then B".

### 6. MAJOR · §2.5, S4 · Runtime failures for installed mods are already answered: not observable

**What's wrong.** The reference states the dim `<plugin>: … skipped` line reaches the transcript only "while the session hot-reloads a plugin folder"; "in any other session that line goes to the debug log alone" (reference §Developing one, 3rd paragraph; same for `ui.render … refused`). So a `session.append` hook with `door: 'notice'` would only see dev-folder failures, and S4 is a "no" for installed mods.

**Fix.** Mark S4 closed. Drop `health.failures` for installed mods from the `Mod` type or scope it to dev mods explicitly. If runtime failures matter, spike reading the debug log file with `$.fs` (path and format in M0) and treat it as best-effort.

### 7. MAJOR · §5.2 · The pane is designed as a dialog and as a sidebar at once, and the layout numbers do not fit a docked pane

**What's wrong.** `holdToasts` is documented "For a dialog the person answers and leaves, not a pane that stays" (7193); while it is shown every other plugin's toast and the engine's wait (7186–7191). `closeOnEscape` also closes the pane on Escape "at an idle, empty prompt once the prompt has the keys again" (7177–7179): clearing a prompt with Esc while modmgr is docked closes modmgr. Yet the plan wants background refresh, detector progress "in the tab", and a tab badge: sidebar behaviour. Arrow-key row movement is only available in dialog mode ("Tab and the arrows walk its buttons", reference §Drawing; a plain focused pane: "the arrows scroll", d.ts 9992), so the ↑↓ keymap presupposes the dialog trio. Layout: a docked pane's `bodyColumns` is "the share" of the terminal (7212), typically 40–70 cells on a 160-column terminal; `columns` is "a request, not a grant" (7210). The 120-column wireframe and the split at ≥ 100 body columns will almost never apply when docked; inline (main screen) gets full width but only "a third" of the rows (7203). `e.viewport.rows` is "Cells down the whole surface, not the room left" (RenderViewport); windowing must use `e.props.scroll.bodyRows` (10009–10016).

**Fix.** Pick dialog: `/mods` opens with the trio, the person acts and leaves, and background work reports through the band, status line and tab title (an open id "retitles", 2414: `$.ui.open({id, title: 'mods · 2 updates'})` is a free badge). Drop the long-lived-pane expectations from §5.1/§5.3. Design the primary layout for 50–70 columns stacked, and treat split as a bonus at ≥ 100. Window rows with `scroll.bodyRows`. State in the footer "ctrl+x tab to focus" when `!e.props.isFocused`.

### 8. MAJOR · §5.5 · The Esc cascade is not implementable as written

**What's wrong.** No key event reaches a plugin from a pane (only `Client` has `onKey`). Esc produces `ui.close` with `origin.kind: 'person'` (7111–7137); a hook "that answers without `next` keeps the pane open on `plugin` and `person`". So "close overlay → clear filter → back → close pane" requires a `ui.close` hook on modmgr's own id that performs one step and denies the close. Workable, but it must be designed (and the deny must never fire on `unload`).

**Fix.** Document the `ui.close` interception in §3 and §5.5; limit it to two steps (overlay/filter, then close) so Esc never feels stuck. Note that `focus: true` is refused while the composer holds text (7165–7171), so `/mods` typed with trailing text opens unfocused: show the focus hint.

### 9. MAJOR · §9 Tests · The coverage and fixture claims cannot be met with `claude plugin test`

**What's wrong.** `claude plugin test` runs files "in an environment like the one the mod's hooks run in" (`test --help`): no Node, no `fs`, no coverage tool; "The kit exercises the plugin's hooks … not any surface's paint" (reference, testing 173). "≥ 95 % branch coverage" is unmeasurable there. "Fixtures are real CLI JSON": only `.ts/.tsx/.js/.mjs/.cjs/.mts/.cts` files load (header line 21), so `.json` fixtures cannot be imported and cannot be read from disk. The "fake CLI via a `process.run` hook beneath the plugin" **is** valid (`'process.run'` is an op event, 6917; test `on` sits beneath the plugin, 14478) and `mock.clock/store/env` exist (14983–15010). "Press every hotkey" is not a kit act: `press` is by `key` (15118), so hotkey rules are a domain test over `keymap.ts`.

**Fix.** Two runners: `domain/` is pure TS, so run it under node + vitest with c8 in CI (coverage is real there); fixtures as `.ts` modules exporting the captured JSON; `claude plugin test` for `services/` and `ui/`. State in §9 which tests run where.

### 10. MAJOR · §2.1 Load-first fix · Scope, durability and the "in practice" caveat

**What's wrong.** F3's "key order of `enabledPlugins` (in practice, install order)" is one file; the merge across `user`/`project`/`local`/`policy` (11481) and managed `prepend`/`append` tiers (TIERS, 12270) decides the real order, and modmgr at user scope cannot precede a `prepend` managed plugin or, possibly, a project-scope mod. Durability: the next `claude plugin install` appends/rewrites `enabledPlugins`, and any engine write to `settings.json` may reorder keys; the fix is undone silently. The settings backup goes to `$.store`, which per finding 2 may reject. Effect is next session only (the engine's in-memory settings are not re-read).

**Fix.** Spike S7 covers cross-scope order. Scope the fix to "within the file of modmgr's scope", label the Health card "takes effect next session; re-check after installs", re-verify on every `session.start`, and abort the write when the backup `set` fails. Write with the file's existing indentation and a trailing newline; refuse if the file is not strictly JSON.

### 11. MAJOR · §6, §4 · The catalogue in `$.state` defeats the 16 ms budgets

**What's wrong.** Every `$.state.get` while drawing crosses the host and copies the value; a 500 KB `catalog` atom read per render (and per filter keystroke, each a `ui.input` dispatch) cannot meet 16 ms. "Rows are data-only" does not help if the data is the whole catalogue.

**Fix.** Keep the search index in module memory, rebuilt on load from the CLI (1 s) or the compact store index; `$.state` holds `view`, counts, and the **visible page** (≤ 50 rows). `services/catalog-cache.ts` computes the page on query/sort changes and writes it once (throttled).

### 12. MAJOR · §2.2, §2.6 · Background `marketplace update` races the `--accept-command` sha

**What's wrong.** `--accept-command` "counts as -y for exactly that command, for that plugin and marketplace catalog… If either changed (a refresh that moved the catalog counts), the run refuses and reports the command again" (`install --help`). The update scheduler runs `marketplace update` every 6 h in the background; a confirm left open across a refresh will fail, or worse, the person confirms text that the next `--json` run no longer matches. It is also a network write every 6 h on a plugin that says it does not phone home.

**Fix.** Pause the scheduler while a confirm is open; always re-run `install --json` immediately before passing `--accept-command`, compare `shownCommand.sha256` with what was shown, and re-show on mismatch. Honour `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC` for the scheduler too and say in the FAQ that update checks fetch marketplaces.

### 13. MAJOR · §2.7 · Headless `/mods` cannot reload, and `$.process` is "CLI only"

**What's wrong.** `$.process` is documented "Commands on the host … CLI only" (3425). If a desktop-app- or VS Code-hosted session has no `$.process`, "VS Code: full except `Client`" is wrong: no install, toggle, validate or test there. In `-p "/mods disable x"`, `$.command.run('reload-plugins')` likely rejects (the hook is the one the turn waits on) and the process exits before an idle reload.

**Fix.** Spike **S11**: what `$` has on a desktop-hosted session (`'process' in $`). Feature-detect and degrade to read-only with a one-line reason. In headless, never attempt reload: print "restart to apply" and set `CommandRunResult.exitCode` (1804) non-zero on failure so scripts can branch.

### 14. MINOR · §2.3 Detector · Shape and false negatives

`list --available` keys are `pluginId`, `marketplaceName`, `installCount`, `source`, `version` (not `id`/`marketplace`). `url` sources are whole-repo `.git` URLs (`hooks/hooks.json` at the root), `git-subdir` carry `path` + `ref` + `sha`. Derive `<owner>/<repo>` from the URL, `encodeURIComponent` each `path` segment and reject `..`. A plugin can also declare hooks via the manifest's `hooks` field, so a 404 on `hooks/hooks.json` is not proof of `plain`: fetch `.claude-plugin/plugin.json` as well (same cache key). The 64 KB cap is post-hoc (`$.http.fetch` reads the whole body, 3404); fine, say so. Coverage is better than the plan fears: 3,491/3,544 remote entries have a GitHub sha, so S6 is nearly answered; measure latency only.

### 15. MINOR · §1 S3 · Update detection is partly wrong and partly already documented

3,070 catalogue entries carry `version`, so after `marketplace update` a version compare works for most. "Restart to apply" in `update --help` is answered by the reference: a new version "reaches a session … through `claude plugin update` and then `/reload-plugins`". Folder-marketplace (`readFromFolder`) plugins have no update at all (reference §Developing one), so "capability diff before updating (local-folder sources)" applies to nothing; do the diff **after** for all sources, or pre-fetch `hooks.json` + module at the new sha and run `validate --json` on a temp copy written with `$.fs.write` (it executes nothing).

### 16. MINOR · §2.1, §4 · Scope and identity gaps

`disable --scope` accepts `user|project|local` only; managed plugins cannot be toggled: show a lock. `projectEnabled` (F10) is not in `Mod`; a user-scope mod can be off for this project. Inline ids `<name>@inline` collide across folders; key `disabledGate` by `provenance` + `root`. The d.ts warns "`name`, `root`, `version` and `provenance` are its own word … a rule keyed on them is one a rename walks past" (7422–7424): say so in SECURITY.md. Project/local scope writes touch a shared `.claude/settings.json`: say "this changes a file in the repo" in the confirm.

### 17. MINOR · §5.5 Keymap · Collisions and gaps

Wireframe shows `[i info]` in the Installed detail while `i` = install (Discover). `k` is "cycle kind filter" (Discover) and `[k cancel]` (Job log overlay); if the overlay draws over the view both Buttons are mounted and "two clash, later wins" (1037). `r` means refresh or reload depending on view. Rows must be `Button`s to take focus/Enter; a `Text` row is unreachable by keyboard. `y`/`n` fine. Band uses letters only, good: a bare digit in an empty composer presses a **band** Button (1036). Add `Home/End`-like jumps via hotkeys (`g`/`b`?) since lists are long and arrows walk one row.

### 18. MINOR · §5.1, §5.6 · Glyphs and theme keys

`⚠` (U+26A0) is East-Asian-ambiguous width and misaligns fixed columns in several terminals; use `!` or `▲`. `ThemeKey` has no `accent`/`muted` (12255): map `accent → claude` or `permission`, `muted → subtle`/`inactive`, and keep `success`/`warning`/`error`. Strip ANSI escapes and bidi controls (U+202A–U+202E, U+2066–U+2069) from catalogue text as well as C0 controls: a name with a right-to-left override can spoof another plugin's name.

### 19. MINOR · §4 · `confirm: StateFamily<ConfirmRequest | null>`

A family holds "one value per `id`" and a reference without `id` "does not compile" (11664–11676). One confirm at a time needs a plain value. Also `StateFamily<T>` is `{ readonly byId: T }`, a marker, not a map.

### 20. MINOR · §3, §9 · `types` manifest field and repo layout

The reference describes `types` as the contract of "a plugin that adds a noun to `$`", with "exported names led by the noun's PascalCase name" and "`claude plugin validate` checks the contract" (reference §The types are the reference; header 91–99). A `PluginState`-only file may fail `validate --strict`. Spike **S10** in M0. Marketplace name = plugin name = `modmgr` yields the id `modmgr@modmgr`; fine, but `claude plugin tag` wants the marketplace entry and `plugin.json` to agree, so put `version` in the entry. The hooks-module tsconfig must set `"types": []`, `jsx: react`, `jsxFactory: h` (header 69–76); pnpm/Biome are fine as root dev tooling as long as `plugin/` has no `package.json` of its own (nothing imports packages).

### 21. MINOR · §6 Gate budget · The first judgement does I/O

The gate reads `disabledGate` from `$.store`; the first `plugin.register` arrives during load, before any `session.start`, so the hot path has one awaited store read. Memoise the promise (one read per load), and say "< 1 ms after warm-up".

### 22. MINOR · §7 · Argv hygiene and the second accepted command

Paths passed to `validate`/`test` come from `installPath` and dev folders; require absolute paths (`/`-prefixed, no newline) so none is read as a flag. `install --help` names a second thing that needs acceptance: the `headersHelper` command "that fetches the archive"; show both. Pass `cwd: await $.session.root()` for project/local scope so `/cd` does not move the write. Good property to state: the child inherits `CLAUDE_CONFIG_DIR`, so isolated configs stay consistent.

### 23. MINOR · §8 Landing page · One false premise

"Screenshots come from real `claude plugin test` mounts rendered to text": the kit never paints (reference, testing 173; `MountedMembers` doc). Generate `demo.json` from the `drawn()` tree with a small renderer of your own, or hand-author fixtures that the UI tests also assert against. The rest (Astro, zero JS, Lighthouse 100, < 100 KB, reduced motion) is realistic; add OG-image generation to `pages.yml` and a link-checker, and keep the keymap table generated from `domain/keymap.ts` so it cannot drift.

### 24. MINOR · §10 Milestones · Missing spikes and lopsided sizing

M0 needs S7 (load order across classes/scopes), S8 (`$.command.run` from a `command.run` hook and in `-p`), S9 (what survives `reload-plugins`: pane, `$.state`, running spawn), S10 (`types` field with a `PluginState`-only contract), S11 (`$.process` presence on hosted surfaces), and a `--data-size` baseline. M3 bundles both toggle mechanisms, update, remove and the band; split toggles+reload semantics (M3a) from update/remove (M3b). M5 holds Dev, Health, load-first, conflicts, updates scheduler and capability diff: too much for one PR. Move `SECURITY.md` to M2 (it shapes the gate and the risk model). Add to M6: how the perf budgets are measured inside the engine (`$.clock.now()` around render, debug-log timestamps) before claiming them.

### 25. NIT · §1 F15, §2.3 · Stale numbers

Update F15 to today's 3,544 entries / 2.09 MB / 0.97 s and the per-source breakdown above; the detector's "≤ 400 requests per run" now covers ~11 % of the catalogue per run, so first full coverage takes ~9 runs: say so, or raise the cap when idle.

## Things the plan gets right

- **Spike-first with recorded evidence.** F1–F15 are run, not inferred, and the open questions are named; `{ tier: 'user' }` on `plugin.register` (4353), `e.props.bodyColumns` (9999), `PaneOpenArgs` fields (7148–7218), `Text wrap: 'truncate-end'` (12245), `$.env.get` literal names (3516–3518) and `$.ui.open` from a command ("asked … placed at any width", 2415) all check out.
- **No shell, argv only, validated ids, never `-y`, `--accept-command` only after a press.** This matches how the CLI binds the sha to one command and one catalogue.
- **Fail-open gate with `.catch` and a deliberate reason.** The validator's note is handled; the trade-off (a disabled mod may load if modmgr throws) is the right one for a manager.
- **Pure `domain/`, `$` confined to `services/` + `ui/`, one write path through jobs.** This is what makes the API churn survivable and the fake-CLI tests possible.
- **Never colour alone, theme keys only, honest "when it takes effect" labels.** Daltonized themes and remote surfaces work for free.

## Additional high-value v1 features

- **Per-mod data size** via `claude plugin list --data-size [plugin] --json`: the CLI already has it; one column in Installed.
- **Tab-title badge** through `$.ui.open` retitle (`mods · 2 updates`): free, visible while unfocused.
- **Debug-log pointer per refused/failed mod**: show the one-line reason the engine logged and a `[c copy]` of the `--debug` command; the only health signal available for installed mods.
- **`/mods export` / `/mods apply <file>`**: a list of ids + scopes (pi-extmgr "profiles"), re-installable on a new machine with the same confirm flow.
- **Undo remove = reinstall same id/version** with one press from the job log; cheap because the CLI pins by sha.
- **"What this mod can see" explainer** built from the d.ts doc comments for each `noun.method` in `uses.calls`: the plain-English chips grounded in the engine's own words.
- **`/mods doctor --json`** for CI and scripts: the Health view as data, with `exitCode` set.
