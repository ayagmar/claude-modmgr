## 1. Findings

### R-M3b-1 (MAJOR) An unchanged update ends in silence

Evidence: `job-runner.ts:250-257` finishes an `up_to_date` (or `from === to`) update `ok, unchanged: true` with
the tail `already so: …`; `jobs.ts:340-346` then makes the batch's reload useless and `job-runner.ts:271-273`
cancels it, so `reload()` never runs and `attention.lastReload` is never set. `Pane.tsx:77` draws
`batchLineOf(queue, attention.lastReload !== undefined)`, and `view.ts:538` returns `undefined` when `showDone` is
false and nothing failed or runs. The Jobs overlay draws a job's tail only while it runs or after it failed
(`overlays.tsx:276-284`), so `already so: turn-band is already at the latest version` is drawn nowhere.

Reproduced (fakes, `update-current` fixture): after `u` → `y` → drain, the queue is
`marketplace-update:ok, update:ok:unchanged, reload:cancelled`, `lastReload` is undefined, the batch line is
`undefined`, `view.notice` is undefined, the status line is undefined. The person confirmed "Update quiet-bash",
watched `refresh marketplace fixtures…` then `update quiet-bash@fixtures (1 of 1)…`, and the line vanished. C12
says "an unchanged result reads 'already up to date'"; `doneText` (`view.ts:483-498`) does say it, but only through
a path that cannot be reached: `test/domain/m3b.test.ts:403` passes `showDone: true` by hand.

Why it matters: the update path is the one with no undo. Silence after a confirm reads as failure, and the
person's next move is to press `u` again (another marketplace fetch, another five-minute-timeout job) or to open
Jobs, where a green `ok` looks like an update that happened.

Fix: give a batch that changed nothing the same echo a reload gives. In `drainOnce`, when a reload is cancelled as
useless and its batch has `ok` members, write `attention.lastReload` to the batch's `doneText` (`"already up to
date"`, `"nothing needed changing"`) and arm the same 8 s clear, so the band, the pane's batch line and R-M3a-4's
redraw all work as they do after a real reload. Alternatively, let `batchLineOf` treat "every job finished, the
reload cancelled, at least one `ok`" as done-worthy without `showDone`, and keep the Jobs overlay's tail for
`unchanged` jobs too. Add a service-level test that asserts the drawn line, not only the job's flag.

### R-M3b-2 (MAJOR) `undo` is not idempotent

Evidence: `actions.ts:333-348` reads `queue`, computes `undoPlan`, and either opens the review or calls
`queueBatch`, which enqueues through a plain `state.update('queue', …)` (`job-runner.ts:82-90`) that does not check
whether the plan is still the newest batch. Two `z` before the redraw (a hotkey and an Enter on the focused undo
Button, the same delivery R-M3a-2 described) both read the same queue.

Reproduced (fakes): `toggle` → `apply` → `confirm` → drain → `Promise.all([undo(), undo()])` → the queue is
`disable, reload, enable*, enable*, reload*`: two inverse batches, one for each press. With the fixture CLI both
enables "succeed"; against the real CLI the second answers `already_in_goal_state`, finishes `unchanged`, and
becomes the newest batch, so the next `z` says "The last batch changed nothing to undo" (`jobs.ts:458-463`) and the
redo the person expects is gone. The reviewed path (`install` in the plan) is safe: the second press re-pushes the
same review and `pushOverlay` dedupes.

Fix: make the enqueue conditional, in the same versioned write that queues it:
```ts
await state.update('queue', queue => {
  const now = undoPlan(queue.jobs)
  if (now.kind !== 'ready' || now.batch !== plan.batch) return queue
  return { ...queue, jobs: prune(enqueueBatch(queue.jobs, { id, specs, reload: true }, newId)) }
})
```
(`enqueue` can take a `when(queue) => boolean` guard so `confirm` of an undo review uses it too, see R-M3b-8.) Add
the `Promise.all` test beside R-M3a-2's.

### R-M3b-3 (MINOR) Dismissing the band line does not quiet the status line or the title

Evidence: `bandOf` returns `undefined` when `how.dismissed === text` (`view.ts:617`); `statusLineOf`
(`view.ts:627-636`) and `titleOf` (`view.ts:639-644`) take no `dismissed`. The band's `d: dismiss` writes
`attention.dismissed` (`actions.ts:408-410`), which is not a summary input, so the chrome does not even re-sync on it.

Reproduced (domain): with `dismissed = 'mods · turn-band can now run programs'`, `bandOf` is `undefined` and
`statusLineOf` is still `turn-band can now run programs`. On screen: the person presses `d`, the band line goes, and
`⚠ modmgr: turn-band can now run programs` (F52's warning glyph) stays under the prompt until they open the detail.
The brief's point of one summary was that the three "never disagree"; here the dismissal is the disagreement.

Fix: decide what `d` means and apply it to all three. Simplest: `dismissed` is a summary input (`summaryOf` takes
`attention.dismissed`, as it already takes `attention`), and a dismissed line clears `caps` and `updates` from the
status line and the badge from the title while the band text they would form equals `dismissed`; the "applying"
and "reload to apply" parts stay, since those are owed, not news. Then `dismiss` is a write to a summary key and the
chrome syncs.

### R-M3b-4 (MINOR) The status line and the pane count one batch two ways

Evidence: `summaryOf.pending` counts every active non-reload job (`view.ts:580`), so `statusLineOf` says
`applying N…` with marketplace refreshes (and, from M5, `test`/`validate` jobs) in `N`; `batchLineOf` excludes
`marketplace-update` from `work` (`view.ts:512`) and counts changes.

Reproduced (domain): update all over two marketplaces and three mods, just after confirm: status line
`applying 5…`, pane `3 changes queued…`, review heading "Update 3 mods".

Fix: count what the review counted. `pending` = active jobs whose kind is in `NEEDS_RELOAD` (the changes), and let
the running `marketplace-update` show as `refreshing <name>…` in both lines (`describeJob` already words it). Share
the `work` filter between `batchLineOf` and `summaryOf` so the two cannot drift again.

### R-M3b-5 (MINOR) `d` deletes data here and dismisses there; the confirm label does not say what it now does

Evidence: `keymap.ts:70-78` binds `keep-data` to `d` on `review` and `dismiss` to `d` on `band`. The sets never
mount together (`collisions()` is clean), but the person is one; `d` is a reflex on the band. On the review, `d` is
a state flip (`actions.ts:279-283`) and the only visible change is the red line `Deletes its data (12 KB) for good.`
and the key's own label (`overlays.tsx:60-64`); `y: confirm` reads the same before and after. A `d` then `y` before
a redraw (two presses land, F12 reference) confirms a delete the person never saw.

Fix (pick): change the confirm label with the choice (`y: remove and delete its data`), so what `y` does is on the
key the ring sits on; and consider another letter for the flip (`k` is free on `review`) so `d` stays "dismiss" in
the person's hand. Keep the default as it is.

### R-M3b-6 (MINOR) "Its data was kept" is what modmgr asked, not what the CLI did

Evidence: `undoReview` sets `keptData: undoes.args?.keepData === true` (`view.ts:329`), the remove job's argument.
The CLI's `uninstall --json` answers `keptData` (`test/domain/fixtures/cli-runs.ts:255,270`: `"keptData":false`),
and `parseOpResult` (`cli-results.ts:343-365`) does not read it; the runner records nothing about it on the job.
The plugin test's harness answers a `--keep-data` run with that `keptData:false` fixture (`harness.ts:49`) and the
review still prints "quiet-bash: its data was kept." (`plugin/tests/m3b.test.tsx:77`).

Why it matters: the undo review's promise ("undo restores it as it was") rests on it, and F51 was verified once by
hand; a CLI version that drops the flag, or a data folder that did not exist, would be told honestly by `keptData`.

Fix: parse `keptData?: boolean` into `OpDone`, record it on the finished job (a `Job.result?: { keptData }` or in
`args`), and let `undoReview` say "its data was kept" only when the CLI said so, "its data went with it" when it
said false, and nothing when it did not say.

### R-M3b-7 (MINOR) The retitle ignores its answer, and was checked at one width

Evidence: `chrome.ts:48-51` awaits `ports.ui.open(...)` and discards the result. d.ts:7328-7332 and
13944-13950: an unasked open "waits undrawn below 144 terminal columns, 110 once they asked for that id"; F53
verified that a retitle of a placed pane stays placed at 120 columns, which is above both floors. The live check
ran at 64 and 120 columns (HANDOFF-M3b "Done when"), and C12 does not say the badge was seen to change at 64.
`isPlaced` before the call (`chrome.ts:48`) does not say what the engine does after it.

Fix: read the result; when `isPlaced` is false, log it (`debug`) and record what happened in F53; and run the retitle
live at 64 columns (bump a fixture mod's version with the pane open inline). If the engine does un-place it, gate
the retitle on the last draw's `bodyColumns >= 110` (module memory beside `paneHadKeys`) or drop the badge below
the floor and keep the status line, which has no floor.

### R-M3b-8 (MINOR) After a confirmed remove the ring aims at the removed row; a stale undo review queues what it showed

Evidence: `confirm` pops the review (and the detail, `actions.ts:311-320`) and calls `ringToOverlay()` →
`ringToSelection()` → `selectedRow(view, mods)`, still the removed row until the runner's `onSettled` refresh; the
ring lands on `row:<removed>` and is lost when the refresh redraws the list without it (F46/F50): Enter does nothing
until an arrow. Second, an undo review is built from the queue at `z` and queued at `y` without rechecking
(`actions.ts:305`): a band `[l reload]`, a second surface, or a reloaded module's resume can change the queue in
between; the install still runs. Low likelihood, but the review's "Undo the last batch" would no longer be the last.

Fix: on a confirm whose targets include a `remove`, move `view.selected` to the neighbouring row before placing the
ring; and give `confirm` of an `undo` review the same guard as R-M3b-2 (the review can carry `plan.batch`).

### R-M3b-10 (NIT) A notable line's name can come from an unvalidated queue target

`undoReview` names a mod `rows.find(...)?.name ?? nameOf(spec.target)` (`view.ts:319`) and pushes
`${name}: ${notableText(id)}` into `review.notable`, drawn as `<Text>{line}</Text>` (`overlays.tsx:115`). The M3a
review accepted the unsanitised notable line because `ModRow.name` derives from a `PLUGIN_ID`-validated id; a
queue job's `target` is validated only when it runs (`argv.ts:154-161`), not when drawn, and the queue is `$.state`
an older module wrote. Sanitize the name in `undoReview` (as `doneText` does, `view.ts:496`) or validate it with
`parsePluginId` first.

### R-M3b-11 (NIT) Wording

- `undoPlan` says "An update can't be undone: the CLI can't install an older version" when the batch's update was
  `unchanged` (`jobs.ts:458`): nothing was installed; "already up to date, nothing to undo" is the truth.
- `doneText` says `quiet-bash installed` for an undo's reinstall (`view.ts:497-498`); the review said "reinstall".
- `statusLineOf` says `applying 1…` for a running `test` or `validate` job once Dev lands (see R-M3b-4).
- The update review's "Its new code runs after the reload" presumes an update exists; modmgr has not checked
  (C12: detection is M5b's). "If a newer version exists, its code runs after the reload" is honest about it.

### R-M3b-12 (NIT) The chrome depends on a runtime write following every action write

`runtime.ts:109-112` wraps the runtime's state port so the runner's and registry's writes to `attention`, `queue`
and `mods` schedule a sync; `createActions` gets the render dispatch's plain ports (`register.tsx:170-172`), so
`queueBatch`'s `enqueue`, `reload`'s `enqueueReload` and `dismiss` do not. Today each is followed by a runner claim
or a registry write, so the status line catches up; R-M3b-3's fix (dismiss as a summary input) breaks that
assumption at once. Either hand actions `rt.ports.state` for the summary keys, or call `rt.chrome.schedule()` from
`queueBatch`, `reload` and `dismiss`, and say which in a comment on `SUMMARY_KEYS`.

### R-M3b-13 (NIT) The stored LRU order lags

`recordCaps` (`caps-history.ts:49-63`) `lruSet`s every sighting (moving it to the end) but `changed` is true only
when a record's content changed or the trim dropped something; a refresh that reorders without changing content
writes nothing (right, F16), so the order on disk is the order of the last content change. With the cap at 300 and
installs rarely past 20 mods it cannot bite; note it in the comment so nobody "fixes" the no-write.

## 2. What is right (worth keeping as is)

- **Review as the one gate.** `update`, `updateAll`, `remove`, `apply` and a reinstalling `undo` all go through
  `openReview` (`actions.ts:196-200`), which places the ring on `act:cancel`; `confirm` is the only path that queues,
  and it is compare-and-set. The review draws the exact argv lines (`commandLine`, `overlays.tsx:168-180`) and, for a
  remove, the data's fate in words and tone.
- **Data kept by default**, in the spec (`keepData: true`, `view.ts:280`), in the argv (`--keep-data` only when
  true, `argv.ts:135`), in the inverse of an install (`jobs.ts:425`), and in the default when a review has no
  `keepData` at all (`review.keepData !== false`, `view.ts:357`). The `d` key is offered only when a data folder
  exists.
- **Undo semantics.** `undoPlan` inverts newest-first, skips reload-only batches, refuses while a batch runs, refuses
  an update with the reason, and skips `unchanged` jobs; `undoReview` names what comes back from `capsHistory` even
  for a mod no longer listed (`registry.ts:208-214`), and warns about the declared command (C10).
- **Capability diff.** `nextRecord` (`caps-history.ts:29-40`) is small and right: first sight records, same version
  changes nothing, carried items survive a later update "since" the first one, a dropped item is no longer new;
  `readCapsRecord` checks `added`/`since` together; `KEY_VERSIONS` with a per-key envelope and the `newer` guard is
  the right shape for a store two modmgr versions may share. `runningVersion` (F51) keys the analysis and the diff
  on what actually runs.
- **Acknowledgement UX.** Enter acknowledges and the detail on screen keeps "New since 0.3.1" until it is left
  (`registry.ts:216-224`, found live, C12): the row, band, status line and title let go together.
- **One summary.** `summaryOf` → `bandOf`/`statusLineOf`/`titleOf` (`view.ts:566-644`) is the right factoring; the
  chrome's coalesced sync with `shown` starting at `null` (a reloaded module re-sends), status only on change, and
  retitle only when the title differs and the pane is placed (`chrome.ts:31-51`) follow d.ts:2440-2449 and
  d.ts:7355-7395.
- **API use**: `$.ui.status` from a `$.clock.after` callback (d.ts:3434 shows exactly that); `UiPane.isPlaced`
  and `.title` (d.ts:14000, 14016); `uninstall --keep-data`, `update --scope`, `marketplace update <name> --json`
  (F8, F51, C10); `list --json --data-size` (F33).
- **Footer from what applies** (`Pane.tsx:85-150`, `footerRowsFor`): a key drawn is a key that works, rows counted
  from the labels; `reviewRows` counts wrapped lines so R-M3a-8's clipping holds for the taller reviews.
- **Tests**: the done criterion is proven end to end (`bumpTurnBand` → row, detail, band, status line, title) on
  fakes and on both surfaces; the shape tags agree between `state.ts` and `register.tsx`; the keymap has no
  collisions with `d` added.

## 3. Before M4 (install from Discover, the declared-command review, sha re-verify)

- **Install is the undo review's `install` plus a sha.** `ReviewRequest.declaredCommand` and `headersHelper` exist
  (`types/index.d.ts:130-131`) and nothing fills them yet; the runner's `needs-acceptance` → `conflict` path
  (`job-runner.ts:237-248`) is the pre-check. M4's review must show `shown.command` sanitised, carry `sha256` into
  `args.acceptSha`, and re-run the pre-check right before enqueueing (C4, F25: any catalogue revision changes the
  sha). Give `confirm` the guard from R-M3b-2 so a sha reviewed is the sha queued.
- **Fix R-M3b-1 first**: an install that is already installed (`already_in_goal_state`) will hit the same silence.
- **`undo` of an install** removes with `--keep-data`; once installs exist, R-M3b-6's `keptData` is the honest input
  for the following undo review.
- **Status line budget.** With `attention.updates` live in M5b, `statusLineOf` will say `2 updates · turn-band can
  now run programs · reload to apply` under every prompt until acted on; decide a cap (one clause, the most
  important) before the scheduler makes it permanent, and settle R-M3b-3 so `d` can quiet it.
- **`capsHistory` for Discover**: the record for a mod never installed does not exist; the install review's
  "what it can do" comes from `validate --json` on the fetched copy (PLAN §12 defers the pre-install diff), so say
  "not inspected yet" rather than drawing an empty notable list.
- **Retitle at 64 columns** (R-M3b-7) before the badge gains `updates`.
