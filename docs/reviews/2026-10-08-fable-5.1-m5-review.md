## 1. Findings

### R-M5-1 (MAJOR) The scheduler spins when checks are off and a stored check is past due

Evidence: `services/updates.ts:91-93` returns `'off'` before anything is stored when `hours <= 0` or the traffic switch
is set; `tick()` (`82-89`) calls `arm()` for every outcome but `'busy'`; `arm()` (`113-122`) computes
`nextCheckIn(lastAt, hours, now)` with no look at the switch, so with `lastAt` past due it is `0` and
`schedule(0)` fires `tick()` again at once (`76-79`). The env is read on every lap (`runtime.ts:193-194`,
`trafficIsOff`), as is the clock. With nothing stored the first-check floor makes it a 60 s lap instead
(`arm()` line 121), and since `'off'` never writes `at`, that lap runs for the whole session.

Reproduced (fakes): store `updates { at: 1 }`, `updateCheckHours: 0.1` (any period the stored time is past; 6 h with a
check from yesterday is the common case), `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1`; `arm()` then `advance(0)` →
**41 `clock.after(0, …)` calls in zero elapsed time**, bounded only by the test's cap on `after`. Without a stored time:
61 `after(60 000)` calls over one simulated hour and `store.get('updates').at` still undefined.

Why it matters: the switch is the documented way to run modmgr without network (SECURITY.md, PLAN §2.6), and the
spin starts at `session.start` of every later session (`lifecycle.ts:65`), in a hook chain. Each lap is three host
round trips; it is not a tight CPU loop in the plugin's own thread, but it is unbounded work the person asked
modmgr not to do. `updateCheckHours: 0` is safe (`nextCheckIn` returns undefined) because `hours` is read in
`arm()`; the switch is not.

Fix: make the off state terminal in both places. In `arm()`, return without scheduling when `hours <= 0` or
`await deps.trafficOff()`; in `tick()`, stop on `'off'` (no re-arm) and keep `'busy'` → retry, `'queued' |
'nothing'` → `arm()`. Health already says why checks are off (`services/health.ts:69-74`), and "check now" still
answers `'off'`. Add two vitests: traffic on + stored past-due → exactly one check at once; traffic off + stored
past-due → `clock.pending` 0 after `arm()`.

### R-M5-2 (MAJOR) The "sure" rule disagrees with the CLI, and a wrong guess never clears

Evidence: `domain/updates.ts:49-65` says an update when `listed.version` (the marketplace file's declared version)
compares newer than `installed.version` (what `list --json` reports), and C15 calls that "sure". F58 says the CLI
"decides by version string" without saying which. Live, in an isolated config with the official marketplace cloned
(`marketplace.json` 190 KB, 315 entries, 14 with `version`): `pyright-lsp` (declared `1.0.0`, **no** `plugin.json`)
installs as `1.0.0`; `security-guidance` (declared `2.0.11`, `plugin.json` `2.0.11`) as `2.0.11`. After editing the
clone's file to declare `1.0.1` and `2.0.12`: `update pyright-lsp` → `updateOutcome: updated, 1.0.0 → 1.0.1`;
`update security-guidance` → `up_to_date, "already at the latest version (2.0.11)"`, and `list --json` still says
`2.0.11`. So the CLI's version is the plugin's own manifest when it has one and the marketplace's declaration only
when it doesn't. modmgr's rule reads the declaration first (`updates.ts:56-59`) and would say "2.0.12 is available".

Reproduced (fakes): store `found { sdk: { from 1.0.0, to 1.2.0 } }`, the fake `update` answering the CLI's real
`up_to_date` line → the job ends `ok, unchanged: true` (`job-runner.ts:302-305`), the registry refreshes
(`runtime.ts:98`, `onSettled`), and `mods[sdk].updateTo` is **still `1.2.0`**, `attention.updates` still 1: the next
check recomputes the same `found`, and nothing in the runner, the registry or `check()` removes an entry the CLI
has just refused. The person sees `↑`, `mods · 1 update` in the title, the band, the status line and a Health item
"1.2.0 is available → update" until the author fixes their file.

Why it matters: this is the feature's promise (C15: "says an update only when sure … everything else is unknown").
The disagreeing case is a marketplace that declares versions and a plugin that also ships one: drift between the two
is exactly how a hand-maintained marketplace file ages. The second half (no clearing) turns any false positive,
including R-M5-6's, into a permanent one.

Fix: (1) In `checkOnce` (`services/updates.ts:124-144`), for a relative source read
`<installLocation>/<source>/.claude-plugin/plugin.json` (paths through `safeSegments`, as Dev's `marketplaceFolderOf`
already does) and let `manifestOf(text)?.version` be the entry's version when present; use the declaration only when
the manifest is missing or has no version; a `url`/`git-subdir` entry with a declared version is not on disk, so it is
unknown (the detector's probe already fetches that manifest at the pinned sha but keeps only `[sha, kind]`,
`store-schema.ts:19`; carrying its version is a later option). Record in F58 which string the CLI compares. (2) In
`runtime.ts` `onFinished`, when an `update` job ends `unchanged` drop `found[job.target]` (or call a small
`updater.forget(id)`), so a wrong guess costs one `u`. Add vitests for both: a declared version with a manifest that
disagrees → no update; an `up_to_date` update → `found` without that id and `attention.updates` 0.

### R-M5-3 (MINOR) "Check now" does not re-arm, and the guard sees only `queued`

Evidence: `actions.ts:790-794` calls `rt.updater.run()`; `run()` (`services/updates.ts:91-111`) writes `at` and
queues, but only `tick()` re-arms (`88`), so the timer armed at start-up still fires at its old time. The `when`
guard (`106`) refuses only while a `marketplace-update` is `queued`; one that is `running` lets a second batch in.

Reproduced (fakes): `arm()` (first check at 60 s), `run()` at t=0 → queued and run; at t=60 s the armed tick → a second
`marketplace update claude-plugins-official`: two refreshes within a minute. With the fake CLI hanging on
`marketplace update`: `run()` → `running`; `run()` again → `queued` beside it; both ran.

Why it matters: a marketplace refresh is a network fetch and a 5-minute-timeout job that holds the queue (and an owed
reload, R-M5-10) while it runs; the person pressing "check now" twice, or once just before the timer, pays for two.

Fix: `run()` re-arms after `'queued'`/`'nothing'` (move the `arm()` call from `tick()` into `run()`, or have `fix`
call `arm()`); the guard uses `isActive(job)` (`domain/jobs.ts`), as `devRun`'s does (`actions.ts:738`).

### R-M5-4 (MINOR) The debug log read: whose log, and a log too big to read

Evidence: `services/health.ts:42-55` lists `<config>/debug`, and if an entry is named `latest` reads it. F35:
`latest` is a symlink to the newest `--debug` session's log. The current session is not necessarily that one: a
person who ran `--debug` last week and not today sees "a hook failed: tool.call (Error) (debug log)" as a **bad** item
with no time, and `debugLog: true` makes Health drop its "logged only under --debug" hint. The read is capped by the
engine at 4 MiB (d.ts:3192, 3200); a debug log of a long session passes that easily, and the `.catch(() => '')` on
line 53 (the comment on 52 knows) turns it into `{ found: true, failures: {} }`: "there is a log and nothing
failed".

Reproduced (fakes): `dirs['/cfg/debug'] = [latest]` and a read that rejects → `health.debugLog === true`,
`health.logged === {}`.

Why it matters: Health's one promise is to be honest about what it knows (PLAN §5.1 "Honest"); a stale "a hook failed"
is a false alarm against a named plugin, and a silent empty read is a false all-clear.

Fix: read `<config>/debug/<session id>.txt` (`ports.session.id()` exists for Dev; d.ts:2768 "the transcript file's
name", and F35 names the file by session id), so `debugLog` means *this* session writes one; keep `latest` only as a
fallback labelled with its file name. On a refused read, keep an item: "the debug log is too large to read here
(> 4 MiB); grep it for `hook failed closed`" rather than an empty table. Privacy is otherwise fine: the whole log is
read into the plugin's memory and only `loggedFailures`' three captures survive (`domain/health.ts:294-305`), matching
SECURITY.md §Update checks and Health.

### R-M5-5 (MINOR) Stacked Health has no way to read a clipped item

Evidence: `ui/Health.tsx:37` draws each item in a one-row `overflow="hidden"` box (C15's live fix for the window
count), and Enter is the fix (`ui/Health.tsx:42`, `onPress → v.act.fix`). At 64 body columns the text column is
`64 − 2 − 17 − 1 − (fix + 1)` ≈ 33 characters (`Health.tsx:25-27`); a failure item is "2 failures while it reloaded;
last: reload failed, the previous version stays loaded: /home/…/hooks/register.ts, compiled line 3" (up to 300
characters, `domain/health.ts:128`), and the logged item up to 160. The split shows the item whole
(`HealthItemDetail`, `Pane.tsx:400`); the stacked layout, PLAN §5.2's primary one, shows 33 characters and offers
only to run the fix on it.

Why it matters: the items that matter most (failures, validate errors) are the long ones, and the person at 64
columns is asked to press "→ validate" on a line they cannot read.

Fix: in the stacked layout make Enter push a `detail` overlay drawing `HealthItemDetail` plus the fix as a
`KeyButton` (Dev's shape: `openDev` then `v`/`t` in `dev-detail`); or draw the selected item's full text as a wrapped
block under the list, counted in `listRows`. Either way the split keeps its behaviour.

### R-M5-6 (MINOR) A hostile marketplace file's version string is carried whole

Evidence: `marketplaceEntriesOf` (`domain/updates.ts:20-33`) keeps `version` and `name` uncapped and unvalidated;
`updateOf` returns `listed.version` as is (`58`); `compareVersions` (`domain/version.ts:7`) matches
`/^(\d+)\.(\d+)\.(\d+)/` with no end anchor, so `1.2.0` + anything is "newer than 1.0.0". The result goes to the
store (`updates.found[id].to`, capped by nothing: `store-schema.ts` `CAPPERS.updates` is identity) and to `$.state`
(`ModRow.updateTo`, `registry.ts:177-180`), every read of which copies it.

Reproduced: `updateOf({ version: '1.0.0' }, { version: '1.2.0' + 'x'.repeat(1e6) })` → a **1,000,005**-character
string. Also: an installed version of twelve hex digits that is the plugin's own (a `202601011200`-style stamp)
passes `COMMIT_VERSION` (`updates.ts:36`) and, against a pinned sha, reads as a moved commit → "update to
ffffffffffff", which the CLI would call up to date (sticky until R-M5-2's fix 2).

Why it matters: a marketplace is the root of trust (SECURITY.md), so this is robustness, not a hole; but the store
budget is < 1 MiB and the `$.state` rows are read on every render. The file itself is bounded: `$.fs.read` refuses
over 4 MiB (d.ts:3200), the official file is 190 KB, and `parseJson` is total.

Fix: in `marketplaceEntriesOf`, keep `name` only when `isPluginName(name)` and cut `version` at 64 (as `manifestOf`
does, `domain/dev.ts:179`); in `updateOf`, say newer only when the whole string is a version
(`/^\d+\.\d+\.\d+(?:[-+][\w.-]{0,40})?$/`); keep `COMMIT_VERSION` but require the pinned-sha rule only when the
installed version is **not** also a parseable version (it already can't be both) and let R-M5-2's clearing cover the
rest.

### R-M5-7 (MINOR) `failureOf` and the folder a notice names

Evidence: `domain/dev.ts:295-300, 311-323`. `HOOKS_FILE` is `(\/[^\s:`'"]+?)\/hooks\/[^\s/:`'"]+`: a path with a
space cannot be crossed, so for `…: /home/me/My Mods/broken/hooks/register.ts, compiled line 3` the folder captured is
`/broken` (reproduced); `foundAt('/broken')` then fails and the failure never gets its folder, so the broken mod never
joins Dev (C14's "a failing folder Dev doesn't list yet joins it"). `FAILURE` matches any of
`fail|failed|refused|skipped|threw|not loaded|did not load|error(s)` anywhere in the text, so a notice
`foo: 3 errors were skipped by the thing at /tmp/evil/hooks/x.ts` is a failure of `foo` at `/tmp/evil` (reproduced),
and `once()` reads `/tmp/evil/.claude-plugin/plugin.json` and, if it names `foo`, lists a row whose `t` runs that
folder's tests.

Why it matters: only the engine writes `notice` rows (a plugin's `$.session.append` is door `note`, d.ts:10464-10467;
the `local_command` subtype, d.ts:10549, is the engine's record of a slash command's output, whose text a plugin's
command answer could shape: a suspicion, not tested), so this is about the engine's wording drifting and about paths
with spaces (macOS `Application Support`, any "My …" folder), not about a hostile plugin. The person's own key press
runs `t`, and the row says its path.

Fix: capture the path up to `/hooks/` allowing spaces (`(\/.+?)\/hooks\/[^\s/:`'"]+` anchored after the F57 phrase
`: ` and before `,` or end), and record a folder only from the phrases F57 verified (`reload failed`, `did not load`,
`hooks module …`), keeping the count for any other failure word. Say in SECURITY.md §Notices that the folder a
notice names is read for one manifest and listed only when that manifest names the same plugin.
