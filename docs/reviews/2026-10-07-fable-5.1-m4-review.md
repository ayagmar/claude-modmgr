## 1. Findings

### R-M4-1 (MAJOR) A ring move onto a local row runs `claude plugin validate` inside the focus hook

Evidence: `register.tsx:267-276` awaits `actionsOf($).focusFound(found)` inside the `ui.focus` gating hook;
`actions.ts:521-528` awaits `rt.catalog.inspect(id)` for every local entry (`folderOf(id) !== undefined`);
`catalog.ts:167-187` runs `validateRoot` (a child process) and sets the memo **after** the await (line 184), with no
in-flight promise and no concurrency limit; `catalog.ts:106` clears every inspection on each catalogue read (the 6 h
refresh, `r`, every install/remove/marketplace job). Measured here with an isolated config:
`claude plugin validate --json test/fixture-mods/spawner` takes 248–346 ms (three runs), turn-band 306 ms.

Reproduced (fakes): `Promise.all([inspect(SDK), inspect(SDK), inspect(SDK)])` runs **three** validates; focusing
each local row of the first window in a row (what holding `↓` does) runs one validate per row, all concurrent; with
the validate answer gated, `focusFound` does not settle until it answers, so the `ui.focus` chain is held with it.

Why it matters: PLAN §6 budgets a row move at **< 16 ms** and validate at "cache misses, 3 concurrent"; the official
marketplace is a clone whose entries are relative sources (20 of the fixture's 201 entries; all of the official
marketplace's plugins in practice), so the common case is the slow one. Holding `↓` over twenty local rows spawns
twenty `claude` processes, each redrawing the window when it lands (`show()` from `inspect`, line 185), and the
focus chain waits on the first. On a reload the memo is gone and it all runs again, while the registry already caches
analyses per `root@version` in the store's `validate` key (C10) and limits them to three at a time.

Fix (in order of value): (1) never await the inspection in the focus path: write `found`, `show()`, then `void
inspect(id)`; the detail redraws when it lands. (2) Memoise the **promise** under `memoKey` before awaiting, so
concurrent callers share one child. (3) Put inspections behind the registry's three-slot limiter (or a small one in
`catalog.ts`) and cache the result in the store's `validate` key by `folder@version` so a reload or a new session
reads it back. (4) Make `inspections.clear()` on a catalogue read keep entries whose version is unchanged. Add a test
that two concurrent inspects of one id run one validate and that `focusFound` resolves before validate answers.

### R-M4-2 (MAJOR) Idle-only does not hold once a subagent runs

Evidence: `register.tsx:230-242` observes `turn.start` (`onTurn(runtime, true)`) and `turn.complete`
(`onTurn(runtime, false)` in a `finally`); `lifecycle.ts:80-82` → `detector.setBusy(busy)`; `detector.ts:209-216`
stores a **boolean** and wakes every waiter when it turns false. d.ts:13160-13173 (`TurnCompleteFields`): "a
subagent's run raises no `turn.start`, its steps carry it"; `agentId?`: "Every hook sees a subagent's turn, so a hook
that spawns sees its children's turns too". So the sequence `turn.start(main)` → `turn.complete(agentId: a1)` →
… → `turn.complete(main)` flips `busy` to false at the first subagent's end, and the six workers probe while the
person's turn is still running, exactly what PLAN §2.3/§6 ("idle only, paused while a turn runs") and SECURITY.md
("only while no turn runs") promise not to do. Every `turn.complete` after that is a no-op flip; a later
`turn.start` pauses again, so the breach lasts to the end of the main turn.

Why it matters: subagents are routine in Claude Code sessions; the harm is bounded (≤ 6 requests in flight, ≤ 600 a
session, no credentials), but the promise is written down in two places and the detector is the one component that
touches the network on its own.

Fix: track turns by id. Keep a `Set<string>` of running turn ids in the lifecycle (or the detector): add
`e.turnId` on `turn.start`; on `turn.complete` remove it only when `e.agentId === undefined` (or when the id is in
the set); `setBusy(set.size > 0)`. Vitest: `start(main)`, `complete(a1, agentId)`, assert no fetch; `complete(main)`,
assert fetches. The d.ts also says `turn.start` is "before its first model call" (d.ts:4416), so a turn that never
reaches a model (an aborted prompt) raises no start and needs no bookkeeping.

### R-M4-3 (MINOR) A stale catalogue window can land after a newer one

Evidence: `catalog.ts:112-140` `show()` reads `view` (line 114), computes, then **replaces** `catalogPage` (line
133) with no check that the view it read is still the view. Two callers overlap in practice: the person's navigation
(`focusFound`/`filter`/`edge` → `showCatalog()`, `actions.ts:243-247`) and the detector's `flush()`
(`detector.ts:100-108`: `invalidate()` then `await show()`) every 50 results, from a `$.clock` callback. Under the
real engine each read and write is a host round trip, so the window between A's read and A's write is real.

Reproduced (fakes, one `view` read held): A reads the view with the selection at row 0; the person moves to the last
match and B writes `offset 151`; A's write then lands `offset 0`, and `rows` no longer holds the selected id. On
screen `foundRow` falls back to `rows[0]` (`discover.ts:154-155`), the ring was placed on `found:<last>` which the
redraw no longer draws, and it is lost (F46/F50) until the next flush or keystroke.

Fix: a generation counter in `show()` (`const mine = ++generation` before the read; after the compute, `if (mine !==
generation) return`), or have the detector's flush only `invalidate()` and ask the actions layer to redraw through
one serialised `showCatalog`. Test: hold one read as above and assert the newer offset survives.

### R-M4-4 (MINOR) F54's echo never clears

Evidence: `lifecycle.ts:27-35` writes `attention.lastReload = RELOADED_WITH_MODMGR` when `tookOverReload` is true and
arms nothing; the runner's `echo` (`job-runner.ts:131-142`) and `reload` (155-163) both arm an 8 s clear (C8).
`summaryOf` echoes `attention.lastReload` (`view.ts:647`), so the band, the pane's batch line (`showDone`) and the
status line's "applied" keep saying "Plugins reloaded, modmgr with them".

Reproduced (fakes): after `onSessionStart` over the F54 queue and 60 s on the clock, `lastReload` is unchanged.

Fix: give the lifecycle the same clear (`ports.clock.after(RELOAD_ECHO_MS, …)` that removes it only while it is still
that line); simplest is to export the runner's `echo` as a small helper both use. Test: advance 8 s, assert gone.

### R-M4-5 (MINOR) A local entry whose read failed is "Reading…" forever, and reviewed as "read once installed"

Evidence: `catalog.ts:175-185`: a failed `validateRoot` is logged and memoised as `undefined` under its version, and
`show()` is not called; `Discover.tsx:163-168` draws "Reading what it can do…" whenever a `local` row has no
`notable`; `installReview` marks `uninspected: true` for `inspection === undefined` (`discover.ts:67`) and the review
says "modmgr reads what it can do once it is installed" (`overlays.tsx:207-209`), which is what it says for a remote
entry it *couldn't* read, not for a local one it *tried* and failed (a malformed manifest, a validate error, a folder
the clone no longer has).

Reproduced (fakes, validate exits 1): `row.local === true`, `row.notable === undefined`, `review.uninspected === true`.

Fix: a tri-state inspection (`pending | { failed: reason } | Inspection`); the detail says "Couldn't read it: <reason>
(r retries)", the review says "modmgr couldn't read it before installing; its detail says what it can do once it is
installed" and keeps the warning tone. SECURITY.md's "before install for an entry whose files are on disk" then stays
true in the failure case too.

### R-M4-6 (MINOR) A running detector ignores what a recatalogue added

Evidence: `detector.ts:199-208` `start()` returns while `running !== undefined`; `run()` builds its `queue` once from
`catalog.entries()` (161-168) and the workers drain only that. `runtime.ts:73-77` `recatalog()` (after an install,
remove or marketplace job) calls `catalog.load({ force: true }).then(() => detector.start())`, which is the no-op
case whenever the first run is still going (a 600-request run over an idle session takes a while, and it is paused
through every turn). `progress()` also counts `total: entries.length` including entries whose plan is `unknown`
(not GitHub, no pinned commit, a `command` source), which can never be checked, so "checked 1,804/3,544" never
reaches its total.

Reproduced (fakes, fetches gated): start, add a marketplace entry, `load({force})`, `start()`, release: the new
entry's URL is never fetched; `detect` ends `checked 200 / total 202`.

Fix: `start()` sets `restart = true` while running; `run()` rebuilds its queue and goes again when the flag is set
after `Promise.all(workers)`. Count `total` over entries whose `probeKey` is defined and say the rest ("12 can't be
checked") or leave them out.

### R-M4-7 (MINOR) The install review names the plugin without its marketplace

Evidence: `overlays.tsx:70-71` names a target `rows.find(...)?.name ?? nameOf(id)`; a catalogue entry is never a
`ModRow`, and `nameOf` strips everything from `@` (`view.ts:25-28`). The heading reads `Install aws-serverless`
(the plugin test asserts exactly that, `plugin/tests/m4.test.tsx:54`) and the target line the same name; only the
"Runs" argv line carries `aws-serverless@claude-plugins-official`. PLAN §7 and SECURITY.md: "Names are always shown
with their marketplace" against look-alike spoofing, and an install from Discover is the one flow where the thing
named is not yet trusted (the synthetic fixtures already carry `turn<U+202E>dnab-@evil`, a bidi override).

Fix: for `action: 'install'` (and the accept review) name the target `name · marketplace` or the full id in the
heading and the target line, sanitised as now. The Discover detail already shows `kind · marketplace`.

### R-M4-8 (MINOR) The declared command is cut at 2,000 characters on the review

Evidence: `job-runner.ts:281` keeps `shown.command.slice(0, 4000)` on the job; `overlays.tsx:219` draws
`sanitize(declared.text, { max: 2000, multiline: true })`, whose `truncate` ends a longer text with `…`, under a
comment that says "Line for line, wrapped, never cut (PLAN §7)". A command between 2,000 and 4,000 characters is
accepted (`y`) for a sha the person saw only part of; past 4,000 the sha covers text the job never kept.

Reproduced (domain): a 2,500-character command renders 2,000 characters ending in `…`.

Fix: draw the kept text uncut (the review is already clipped to the body and scrolls as rows), and when the kept text
is itself cut (`shown.command.length > 4000`) do not offer `y`: say "too long to show here; accept it in a terminal" and
keep `c`. Add the hidden-characters warning test and a long-command test at the UI level.

### R-M4-12 (NIT) Detector edges

### R-M4-14 (NIT) The review-time pause of catalogue refreshes

listed" (`actions.ts:543-548`), so nothing wrong happens today; either implement the pause (skip `recatalog` while
`review !== null`, run it on `confirm`/`cancel`) or record in C13 that it is not needed and why.

## 2. What is right (worth keeping as is)

- **One gate for running code.** `install`, the accept review and `marketplace add` all go through `openReview`
  (`actions.ts:266-270`), the ring on `act:cancel`; `confirm` takes the review by compare-and-set; the argv is built
  only from validated parts (`PLUGIN_ID`, a scope enum, a 64-hex sha, a `MarketplaceSource` that is `owner/repo`, a
  clean https URL or an absolute path, `ids.ts:63-83`). The accept review keeps the scope the sha was shown for and
  hides the Select (`overlays.tsx:129-142`), and says "run it and install" on `y`.
- **The CLI's binding as the re-verify** (C13). F25: the acceptance names a sha; a changed command is refused and
  shown again, and the runner turns that into a new `shown` (`changed: true`, `job-runner.ts:274-275`) that `v`
  reviews. This is stronger than a pre-check install, which would install when nothing is declared. The residual trust
  is that `shown.command` and `shown.sha256` describe one command: they come from one CLI answer, so they do. Another
  plugin could rewrite modmgr's `$.state` by hooking its `state.set` (d.ts:3376-3379); such a plugin already runs with
  session power, which is SECURITY.md's "lens, not a sandbox" line.
- **C4 handled honestly.** A refused acceptance sets `degraded.acceptCommand`; the review then offers `c` and the
  exact terminal command, never a workaround (`overlays.tsx:52-59`, `226-230`). `parseOpResult` now recognises the
  refusal with or without a JSON line (`cli-results.ts:322-328`).
- **Probe hygiene.** `githubRepo`/`safeSegments`/`planProbe` (`detector.ts:32-105`) are small, total and tested with
  the hostile fixtures (`../../etc`, backslashes, non-GitHub, no sha → `unknown`); keys are the pinned commit or
  `local:<version>` (`probeKey`), so a cache entry is good for exactly the code it describes; 429/403/5xx pause every
  worker and requeue up to three times; results reach the store in batches of 50 (F16).
- **Idle-only in shape**: `turn.start`/`turn.complete` are observed, never gates, `next(e)` first and `onTurn` in a
  `finally` (`register.tsx:230-242`); only R-M4-2's subagent case is missing.
- **The catalogue stays out of `$.state` and `$.store`** (R2, R11): module memory, a window of ≤ 50 rows around
  `view.found` with its `offset` (`windowOf`), matching memoised per search/kind/sort/kinds-version
  (`catalog.ts:115-121`). Measured here with the real `kindOf` (a `planProbe` per entry): **1.5 ms median over 3,545
  entries, 4.6 ms over 10,000**, well under PLAN §6's 16 ms.
- **Local entries read before install** (F55) and said plainly when they aren't: a remote entry's review says what it
  can do is read once installed (`uninspected`), which is the M3b review's §3 ask.
- **Safe by default**: scope `user` first; project/local say they edit this repository; marketplace add says it runs
  no plugin code and fetches a catalogue; the empty state draws each key once (F12).
- **F54 fix**: `takeOver` finishes a reload left running as `ok` with its line, `tookOverReload` tells the lifecycle,
  and the old runner stops at `queue.owner !== owner` (`jobs.ts:286-308`, `lifecycle.ts:20-35`). `Job.shown` is
  additive, so `queue` stays `/1`; `catalogPage`, `view` and `review` all moved tags, and `state.ts` and
  `register.tsx` agree.
- **API use** matches the d.ts: `SelectProps` (`key`, `options`, `value`, `onSelect(value, e)`, d.ts:10415-10446),
  an uncontrolled `Input` for the marketplace field (`value` optional, d.ts:5458), `$.http.fetch(url)` with no
  `init` (no `auth`, no headers, d.ts:3462), `$.fs.read(path)` with an absolute path (d.ts:3195-3214).
- **Tests** prove the done criterion: a local fixture mod found on disk, read, installed at a scope and loaded
