## 1. Findings

### R-M6-1 (MAJOR) Text writes run beside the runner, not through its queue

Evidence: `services/commands.ts:201-237` (`runWrites`) builds each job `running` in a local, calls `runJob` on the
hook's ports (`220`), and only when every job has ended appends the finished batch to the queue (`227`). Nothing reads
the queue first. The runner's one-at-a-time rule is `nextRunnable` over the queue's jobs (`domain/jobs.ts:86-90`) and
`claim` (`330-333`): a job that is not on the queue is invisible to it. The reload rule is the same: `drainOnce` runs a
queued `reload` once `reloadReadyAt(queue.jobs)` has passed (`job-runner.ts:349-357`), computed from the queue's
`endedAt`s, so a text write in flight moves nothing.

Reproduced (fakes, `createRuntime` + `modsCommand` on one world):
1. Queue `{ owner: 'own', jobs: [enable redactor queued] }`, the fake `enable` set to hang, `runner.kick()`,
   `advance(1)` → the enable is `running`. Then `/mods disable turn-band@fixtures --yes` → `claude plugin disable
   turn-band@fixtures --scope user --json` runs **at once** and answers `✓ disable …` while the queue reads
   `[enable:running, disable:ok]`. Two `claude plugin` writes to the same `settings.json`, concurrently.
2. Queue `[enable ok (endedAt t0), reload queued]`, the fake `disable` hanging, `kick()`, `advance(1)` (the wake is
   armed for t0+1500), then the text `disable … --yes` starts; `advance(2000)` → **`reloads === 1`** while the
   disable is still running; the queue reads `[enable:ok, reload:ok]`. The reload ran in the middle of a CLI write;
   F38 says a reload that close to a settings write applies nothing. (The write then timed out at 60 s in the fake,
   which is only the fake's way of ending it.)

Why it matters: PLAN §2.8 ("Jobs run one at a time… A batch ends with a single `reload` job, which only runs when no
other job is queued or running") is the invariant every other part relies on, and C16 says the text writes are
"recorded like the dialog's". They are recorded, after the fact; they are not *serialised*. The person hits this
whenever a dialog batch is running or a reload is waiting its 1.5 s and they (or a script in the same session) run a
text write. A third, narrower race follows from the same gap: the runner's `reload()` clears `reloadPending` *after*
`reloadPlugins()` resolves (`job-runner.ts:255`); a text write that finished during that reload set it `true`
(`commands.ts:231`) and is then cleared, so the person is told nothing is owed although their write was not applied.
That one is a suspicion from the code, not reproduced.

Fix (small, keeps the budget win): before running, take the queue in the same compare-and-set the dialog uses. In
`runWrites`, `enqueue(ports, { id: batch, specs, reload: false }, newId, queue => !queue.jobs.some(isActive))` and
refuse with "a job is running (see /mods → job log); try again when it ends" (exit 1) when it returns `false`; then
claim each job in turn (`claim(queue, rt.owner, id, now)` on the hook's state port, `isClaimedBy` to check), run it on
the hook's ports as now, and `finish` it on the queue the way `drainOnce` does (`369-371`). The jobs are then
`running` on the queue while they run, so the runner's `nextRunnable` returns `undefined`, a queued reload waits
behind them (and `reloadReadyAt` sees their `endedAt`), the job log and the band show them, and the owner check in
R-M6-6 comes for free. Call `rt.runner.kick()` at the end so a waiting reload resumes. Two vitests: the two
reproductions above, asserting one CLI write at a time and no reload while a text job is `running`.

### R-M6-2 (MAJOR) A remembered Discover tab loads the catalogue and starts the detector at every session start

Evidence: `services/lifecycle.ts:52-66` applies `prefs.tab` to `view` in `background()` on the first `session.start`
of a session; `76-83` then reads `view.tab` and, for `discover`, runs `rt.catalog.load()`, `rt.catalog.show()` and
`rt.detector.start()` (`dev` and `health` get their refreshes). The comment on `75` says what that branch was for: "A
reloaded modmgr with Discover showing reads its catalogue again (module memory)". Before M6 `prefs.tab` was never
written (C16: "Preferences were never written"), so on a fresh session `tab` was always `installed` and the branch
only ran after a reload of modmgr. `actions.ts:349-355` now writes `tab` on every tab change.

Reproduced (fakes): store `prefs { tab: 'discover', … firstRunDone: true }`, surfaces `['terminal']`,
`background(rt, { fresh: true })`, `advance(10)` → the process calls include `claude plugin list --json --available`
and `claude plugin marketplace list --json` (beside the installed refresh and its validates), with no `ui.open` and
no `/mods` typed.

Why it matters: PLAN §6 budgets the catalogue load "on first Discover open" and the detector "≤ 600 probes/session,
idle only"; SECURITY.md promises the detector's reads happen "at most 600 a session, only while no turn runs". A
person who was browsing Discover when they last closed the dialog now pays 0.6 s of CLI (PERF.md) and up to 600
`raw.githubusercontent.com` requests in every later session, including ones where they never open `/mods`, until
they switch tabs. It is also the only path on which the detector starts without the person having looked at
Discover, which the idle-only design did not anticipate. Starting on `dev` or `health` is cheaper (a folder listing,
a debug-log read) but the same shape.

Fix: keep the restore and drop the eager work for a fresh session. In `background()`, run the `tab === …` branch only
when `!how.fresh` (a reloaded module, which is what it was written for); a fresh session loads the catalogue when
the pane opens on Discover, which `actions.tab` already does on a tab press and `openDialog`/the first draw can do
for a restored tab (one `rt.catalog.load()` + `show()` from `modsCommand`'s `open` path when `view.tab ===
'discover'`, or lazily in `drawPane` the way C13's `background()` reload does). Add a vitest: a remembered
`discover` tab with no `/mods` → no `--available` call and `detector` idle; opening the dialog → loaded.

### R-M6-3 (MINOR) The hook still waits on the runtime's ports in two places, inside its budget

Evidence: `services/commands.ts:63` awaits `rt.registry.refresh()` when the registry is not loaded (the comment on
`62` calls that deliberate: "on the runtime's ports (never this hook's)"); `97-98` await `rt.dev.refresh()` and
`rt.health.refresh()` for `doctor`. Both run on the runtime's ports (built at `session.start`, `runtime.ts:70-80`),
so their `$` calls are not "any `$` call of the hook's" (d.ts:5063-5064) and the hook's clock runs through them,
which is precisely what F59 recorded for the queue wait ("waiting on anything else does"). `registry.refresh()` on a
cold cache validates every mod three at a time (`registry.ts` `VALIDATE_CONCURRENCY = 3`, PERF.md: 1.7 s for seven
plugins) and, while a start-up refresh is in flight, `refresh()` joins it (`registry.ts:232-236`), so the hook waits
for the whole of it.

Not reproduced (the fakes don't meter a budget); the arithmetic is PERF.md's: ≈ 0.25 s per plugin at three
concurrent, so a first `/mods list` in a `-p` script against a config with ~40 plugins waits ≈ 10 s and fails
closed with "modmgr failed to answer", the very symptom C16 fixed for the writes. In an interactive session the
start-up refresh has usually finished first; `-p` is the case the text commands exist for.

Fix: for `list`/`info`/`export`, read the installed list on the hook's own ports when the registry isn't loaded
(`listInstalled(ports)` + the registry's pure `rowsOf`, or give `registry.refresh` an optional `CliPorts` argument so
its CLI runs use the hook's `$` while its state writes stay on its own, which is the same split `runWrites` makes).
For `doctor`, don't await the Dev and Health refreshes: Health's items are drawn from `$.state` as they are
(`healthItemsOf` on whatever `dev`/`health` say), and say "facts from <n> s ago" when `facts.at` is old, or refresh
on the hook's ports. Record the rule in C16: the hook awaits nothing but its own `$`.

### R-M6-4 (MINOR) Flags a subcommand doesn't use are accepted and silently dropped

Evidence: `domain/command-args.ts:60-61` and `64-95` (`flagsOf`) accept `--scope`, `--accept-command`, `--yes`,
`--json`, `--wipe-data` for every subcommand; the `enable`/`disable` (`129-133`), `remove` (`134-139`), `update`
(`140-144`) and `apply` (`165-169`) cases read none of `scope`/`accept`, and `commands.ts:142-146` builds a toggle
from the row's own scope.

Reproduced (fakes): `redactor@fixtures` off at `project` scope; `/mods enable redactor@fixtures --scope local` →
"This would run: `claude plugin enable redactor@fixtures --scope project --json`". The flag is not an error and not
what runs. And: an `apply` file naming `cmdmod@cmdmkt` with the fixture CLI refusing the declared command → the answer
ends "To run it, add --accept-command 5e54…5695"; `/mods apply /repo/a.json --yes --accept-command 5e54…5695` parses,
runs `claude plugin install cmdmod@cmdmkt --scope user --json` again **without** `--accept-command`, and fails the
same way. (`stepSpec`, `commands.ts:188-193`, has no `acceptSha`.)

Why it matters: a scope is a settings file; a person asking for `local` and getting `project` edits their
repository's `.claude/settings.json` (the review screen says so, the text path says nothing). The `apply` hint sends
them in a circle. Both are quiet, which PLAN §5.1 "Honest" forbids.

Fix: make `flagsOf` take the set of flags each subcommand allows (`install: scope, accept, yes`; `remove: wipe, yes`;
`enable|disable|update: yes`; `apply: yes` (+ `accept` only if `apply` learns to carry it); `doctor: json`), and
answer `unknown option --scope for enable` (exit 2) otherwise. Then either let `apply` carry `--accept-command` into
its install steps or change the hint under an `apply` to "install it with `/mods install <id> --accept-command
<sha> --yes`". A parser test per rejected pairing.

### R-M6-5 (MINOR) The welcome is spent by the first session that draws, seen or not

Evidence: `services/lifecycle.ts:56-65`: `welcome = draws && !prefs.firstRunDone`; when true the `view` stack is set
to `['welcome']` **and** `prefs.firstRunDone` is written in the same step, at `background()` time, before any
`/mods`. `$.state` is session-scoped, so the stack does not survive to the next session; the store flag does.

Why it matters: PLAN §5.3 "First run: one screen…" is the one piece of onboarding; a person who installs modmgr and
doesn't open it in that same session (the common case: install, carry on working) never sees it. The `-p` rule C16
added is the same thought applied only to headless runs.

Fix: write `firstRunDone` when the welcome is left (`actions.back` when `topOverlay(view) === 'welcome'`, or in
`openDialog` when the pane is placed with the welcome on the stack), not at start-up; keep pushing the overlay at
start so the first `/mods` opens on it. The plugin test "the first session opens on a word of welcome, once" then
asserts the flag after `act:start`, which it nearly does already (`ui.test.tsx:547-553`).

### R-M6-6 (MINOR) No owner check for the text batch; the history write can outlive a `-p` run

Evidence: `commands.ts:227` appends the batch with `state.update('queue', …)` and no look at `queue.owner`; `233-235`
then call `rt.jobFinished`, `rt.chrome.schedule()` and `rt.registry.refresh()` on *this* module's runtime. After a
reload of modmgr the old module's in-flight command hook finishes and its `$` calls still work (F39), so a text write
that spanned the reload writes its jobs into the queue the new module owns and then has the **old** registry rewrite
`mods`/`detail`/`sync` after the new module's start-up did. The runner has `ABANDONED` for exactly this
(`job-runner.ts:77-78`, `337`, `367`, review R-M4-13); the text path has nothing. Separately, the history entry is a
`store.update` (`225`), batched behind `FLUSH_DELAY_MS = 2000` on the runtime's clock (`store.ts:206`, `247-253`);
nothing hooks `session.end` and `runtime.dispose()` is never called (no caller in `plugin/hooks/`), so a `-p` run
that prints the answer and exits (d.ts:1843 "the whole prompt of a headless run") leaves the entry unwritten. C16
says the writes are "recorded… in the history".

Both are suspicions from the code (a reload mid-write and a real `-p` exit are not in the fakes). The first is
narrow (a reload of modmgr's own files during a text write); the second is every `-p` write.

Fix: the first comes free with R-M6-1's claim/finish on the queue (a `claim` that fails because the owner changed
ends the write as abandoned; nothing written, as the runner does). For the second, `await rt.store.flush()` at the
end of `runWrites` (one `$.store.set` on the runtime's ports, a few ms) or, better, hook `session.end` once with
`runtime?.dispose()` + a flush, which also stops the detector and timers cleanly at exit.

## 2. What is right

- **The budget argument (F59) is correct and cited right.** d.ts:5063-5064, 5070-5079 and 3409-3411 say what F59
  says; `runWrites` awaits only `ports.clock.now`, `ports.state.*` and, through `runJob` → `runOp` → `runCli`,
  `ports.process.run` and `ports.session.root` on the hook's `$` (`commands.ts:209-227`, `cli.ts:48-58`). A 5-minute
  install is free. The live `-p` check answered `list`, `export` (JSON after the `modmgr: ` prefix, as F59 says),
  a usage error and a refused write with exits 0, 0, 2, 1.
- **One implementation of a CLI job.** `runJob` (`job-runner.ts:105-189`) is what the runner's `execute` calls
  (`329`) and what the text path calls (`220`): the declared-command stop, the `SHOWN_MAX` cap, `acceptCommand`
  degraded flag, `unchanged`/`up_to_date`, `keptData` are decided once. `test/services/m6.test.ts:123-151` covers its
  refusals.
- **The declared-command path never relaxes.** No `-y` in `argv.ts`; a given sha becomes `acceptSha` on the spec

  `acceptCommandMatched: false` → "changed since it was reviewed" (`cli-results.ts:342`, `job-runner.ts:160-163`);
  the text shows the command whole (sanitised, multiline, ≤ 4000) with its sha and the exact flag to add
  (`command-text.ts:224-234`), and a truncated one goes to the terminal. The sha is checked as 64 lowercase hex
  before it is anything (`command-args.ts:151-153`).
- **`apply` is as narrow as promised.** It reads the one file named (`$.fs.read`, 4 MiB cap d.ts:3200), parses with a
  guarded `JSON.parse`, refuses a non-array `mods`, more than 100 entries, an entry without a valid id or scope, and
  carries nothing from the file into a job but `PluginId` and `ToggleScope` (`command-text.ts:160-189`). Checked
  here: 101 entries → "lists more than 100", `mods: {}` → shape error, `scope: null` → `user`, a `__proto__` key →
  ignored. Enable steps keep the row's own scope (`183-185`), the right call.
- **`export`** is `{ mods: [{ id, scope, version }] }` for CLI-installed mods only (marketplace and folder-marketplace
  at a toggle scope, `command-text.ts:133-146`), which is what `apply` can act on; launch-command, skills-dir and
  managed mods are correctly left out.
- **`doctor` cannot disagree with Health**: `healthItemsOf` on the same eight keys (`commands.ts:99-108`), as the M5
  review asked, with exit 1 iff an item is `bad`; the JSON is a stable projection (`group`, `tone`, `text`, `fix`).
- **The parser** splits on whitespace, treats anything starting `--` as a flag, refuses unknown flags and missing
  values, checks ids/scopes/shas through `domain/ids.ts`, and sanitises what it echoes (`command-args.ts`); every
  shape in `USAGE` parses (`commands.test.ts:26-77`).

## 4. Verdict

**Not yet mergeable; close after R-M6-1 and R-M6-2.** The design is right and F59's budget claim is verified against
the d.ts: running the text writes on the command hook's own `$` is the correct answer to the 10 s budget, `runJob` is
shared rather than copied, the declared-command path is as strict as the dialog's, `apply`/`export` are narrow, and
the headless path works live with the right exit codes. What is wrong is that the text writes were taken *off* the
queue to escape the budget instead of being *put on* it from the hook: they now run beside the runner (two CLI writes
at once, a reload mid-write, reproduced), and the preference fix quietly turned a reload-only start-up branch into a
catalogue load and detector run at every session start for anyone who left the dialog on Discover (reproduced). Both
are small changes with clear tests. The MINORs are a morning's work together; the branch coverage margin is the thing
to watch in M7.
