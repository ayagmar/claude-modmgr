## 1. C2: is "only `register.tsx` spells `$`" sound and maintainable?

**Verdict: yes, and it is the only shape the validator leaves open.** F36 and F37 were re-verified (§A): `$` across an
import is refused (`$ is followed only into a function declared in this same file, never across an import`), storing
`$` is refused (`$ itself is assigned`), a ports object built by a same-file function and passed to an imported
function validates and is traced (`calls: $.process.run (via portsOf)`), nested same-file builders validate, and a
ports object stored at module scope in `session.start` and used by a `ui.render` press handler validates. The runtime
side is backed by the probe: a closure over the `session.start` `$` ran from `$.clock.after` and a closure over a
render dispatch's `$` ran from `onPress` (`s8-s9-s11-s12/interactive-plugin-dir.log`, transcribed; see M6). The d.ts
agrees: `$.clock.after`'s `fn` "stays in the plugin's environment and runs once the dispatch resolves" (d.ts:7079-7082)
and a press handler is "the bottom of the `ui.press` chain", held "for the drawing's life" (d.ts:1142-1151).

### M1 (MAJOR) Builders must be top-level function declarations in the hook file

Scratch test D (§A): a builder defined *inside* `register()` as `const build = ($) => ({...})` is refused with
`$ is passed to "build", which is not a function declared at the top of this file (a function declaration, or a const
bound to one); $ is followed nowhere else`. C2 (PLAN.md:489-497) says "builds typed ports per dispatch: `portsOf($)`"
without this constraint. Write it into C2 and into the layering test: every function in `register.tsx` that takes `$`
is a top-level declaration, `$` appears inside it only as `$.noun.method(...)`, and builders may call other top-level
builders (test E validated `{ ...procPorts($), ...uiPorts($) }`).

### M2 (MAJOR) `.catch` handlers are asked on re-entry with a `$` whose calls reject

d.ts:1155-1160 and 5105-5114: when an event is raised beneath a hook's own `$` call, the hook is skipped and its
`.catch` answers "in its place: its own `$` calls reject". ref:75 spells out the consequence: the handler "decides from
`e` and its own `next` alone". modmgr will hit this: `dev-watch` hooks `session.append` while modmgr itself appends
rows (`$.ui.log`, command answers); the Esc cascade hooks `ui.close` while modmgr closes its own pane. C2 says every
hook "gets a `.catch`" but not what the handler may do. Rule for `register.tsx`: a `.catch` is either the pass-through
`(_$, e, next) => next(e)` (observers, render hooks) or a pure answer (`/mods` returns `{ text }` without `next`, which
also keeps it out of `gatingHooks`, ref:62). No `.catch` builds ports. The layering test should assert that no
`.catch` argument references `$`.

### M3 (MAJOR) F37 makes the "one line each, delegating" claim false for shared events

PLAN.md:64 and scratch test F: a second `on('session.start', …)` without a matcher is refused. `session.start` is
needed by the command registration, the job runner resume, the update scheduler, the capability probe, the pane
re-attach and the first-run check; `session.append` by `dev-watch` and (M5b) health; `ui.close` by the Esc cascade and
the overlay stack; `command.run{command: mods}` by the UI and the non-UI subcommands. `register.tsx` therefore needs
an ordered fan-out per event, which is where sequencing bugs live (the runner must not kick before `prefs` is read;
`session.start` must stay under 5 ms, PLAN §6). Make the fan-out explicit and testable: `services/lifecycle.ts`
exports `onSessionStart(ports, e): Promise<void>` that calls the steps in order, and `register.tsx` has exactly one
`on('session.start')` whose body is `runtime = build($); await lifecycle.onSessionStart(runtime, e); return next(e)`.
Matchers do not collide, so `ui.render` for `Pane`/`AbovePrompt` and `command.run{mods}` stay separate hooks.

### M4 (MINOR) Which `$` drives the job runner

C3 (PLAN.md:503-506) says the runner "is kicked from press handlers and `$.clock.after(0, …)`" without saying whose `$`
it runs on. ref:148-158: work that outlives a dispatch "belongs" to `session.start` and its `$.clock` timers, and
those timers "run until cancelled or until the module reloads". So: the runner owns the port set built in
`session.start` (module-scope `runtime`, rebuilt on every `register`, which F31 guarantees). Press handlers use their
own render-dispatch ports for exactly two things: `update(jobsAtom, enqueue)` and `runtime.kick()`. They never run a
job on a render `$`, whose drawing may be gone by the time a 20 s `claude plugin validate` returns. Scratch test G
validates this shape.

### M5 (MINOR) Reload idempotence and state shape

- ref:152-156: if the engine replaces the worker mid-session, a `$.command.run` made *while* `session.start` runs is
  deduplicated, but one made later from a timer "is made again". So the `reload` job must be written `running` to
  `$.state` *before* `$.command.run({ command: 'reload-plugins' })`, so a resumed runner marks it `interrupted` (C3)
  instead of reloading twice.
- d.ts:716-724: `atom(ref, initial, { shape })` declines a value an older module wrote under another tag. PLAN §4
  versions `$.store` but not `$.state`; give every atom a `shape` (e.g. `'jobs/1'`) so an update of modmgr that
  changes `Job` does not resume against a stale queue.
- d.ts:9251-9256 and ref:71: a `userConfig` change reloads the module and re-runs `register`. That is a third
  resume path beside update and hot reload; add it to the C3 test list (`test(name, { options })` can seed it).
- d.ts:3377: `$.state.set` is refused while a render hook draws. `act` handlers run from `onPress`, so they are fine,
  but a "read then write" from `read` closures captured at draw time is the bug ref:114 warns about; use `update`.

### Testability and re-entry, as asked

- Services with fake ports under vitest: yes, and cheaper than the fake-CLI path, but keep two things in
  `claude plugin test`: the fan-out order (M3) and anything that depends on dispatch rules (re-entry, `state.set`
  during draw, `command.run` rejection inside a `command.run` hook). Those are host behaviours fake ports cannot model.
- `read($, atom)` through a port still subscribes the drawing, because the call happens inside the render dispatch
  (d.ts:9221-9224). A service that caches state in module memory and hands the UI a snapshot would *not* resubscribe.
  Keep `ui/` reading through `ports.state.read` only.
- The validator's `(via portsOf)` notes list every call a builder spells, so modmgr's own capability facts in
  `/mods` are unchanged by the indirection.

### M9 (MAJOR) `--accept-command` from a mod will most likely be refused on SDK-hosted sessions

The CLI's "`--accept-command is ignored inside a Claude Code session`" check fires for the agent's Bash tool and not
for a mod's child in an interactive session. The S12 env captures show the difference: the interactive child's
`CLAUDE*` variables are `CLAUDE_CONFIG_DIR, AI_AGENT, CLAUDE_CODE_ENTRYPOINT, CLAUDE_CODE_MESSAGING_SOCKET/TOKEN`
(`interactive-installed.log`:5), while the `-p` and SDK children also carry `CLAUDECODE`, `CLAUDE_CODE_SESSION_ID`,
`CLAUDE_PID` and more (`headless-p.log`:6, `sdk-stream-json.log`:5). The desktop app runs the engine as an SDK host
(README:149-150), so on the desktop app the mod's install with `--accept-command` will very likely be answered
"ignored inside a Claude Code session" (untested; this is an inference from the env difference, and it needs one run
of `/probe exec install … --accept-command` under `--input-format stream-json` to settle). Two consequences:

- C4's mapping to `rejected` is necessary but the review screen should not send the person through a confirm that
  cannot succeed. Decide up front from `session.start`'s `surface`/`isInteractive` (d.ts:11591-11606): on a
  non-terminal surface, the review screen for a command-sourced plugin shows the command and sha verbatim and offers
  `[c copy terminal command]` plus "accept it in `/plugin` → details", with no `[y confirm]`.
- Do **not** work around it by stripping `CLAUDECODE` from the child's `env` (d.ts:7947-7951 allows setting env). The
  check exists so that a model-driven session cannot accept a marketplace command; modmgr's review screen is a person
  answering a dialog, but the engine cannot tell, and the mod-child message already shows the guard is weaker there
  ("or pass -y/--yes to accept", `install-accept-from-mod-process-run.log`:1). SECURITY.md should say that modmgr's
  review screen is the only gate in the interactive path and that `-y` is never passed.

## 4. Proposed ports interface and file layout

The shape below passed the validator in scratch tests A, E and G. It keeps PLAN §3's intent (domain pure, services
`$`-free, UI never touching process/http/fs) and makes the layering test mechanical.

```
plugin/hooks/
├─ register.tsx            the only file that spells `$`. Top-level builders + one `on(...)` per event + fan-out calls.
├─ ports.ts                interfaces only (no runtime code, no `claude-code` value imports)
├─ domain/                 unchanged
├─ services/
│   lifecycle.ts           onSessionStart(rt, e) / onReload(rt): ordered steps; the only place sequencing lives
│   runtime.ts             Runtime = { ports: Ports; kick(): void; dispose(): void } built once per register
│   cli.ts registry.ts store.ts job-runner.ts updates.ts detector-runner.ts catalog-service.ts capability-probe.ts dev-watch.ts
│                          each exports functions over the narrowest `Pick<Ports, …>` it needs
├─ ui/
│   Pane.tsx views/ …      render(view: ViewPorts, e): tree; handlers close over `view.act`
│   band.tsx
└─ commands.ts             /mods subcommands over `Pick<Ports, 'process' | 'state' | 'store' | 'session'>`
```

```ts
// ports.ts — types only. Each noun is its own interface so services and tests take the minimum.
export interface ProcessPort { run(argv: readonly string[], init?: { cwd?: string; timeoutMs?: number }): Promise<ProcessRunResult>
                               spawn(req: ProcessSpawnRequest): ProcessSpawnHandle }
export interface StatePort   { read<T>(a: Atom<T>): Promise<T>
                               update<T>(a: Atom<T>, fn: (v: T) => T): Promise<void> }   // wraps `update($, …)`, ifVersion-safe
export interface StorePort   { get(key: string): Promise<unknown>; set(key: string, v: JsonValue): Promise<void>; keys(): Promise<string[]> }
export interface ClockPort   { now(): number; after(ms: number, fn: () => void): () => void; every(ms: number, fn: () => void): () => void }
export interface HttpPort    { fetch(url: string, init?: HttpInit): Promise<HttpResponse> }
export interface FsPort      { read(p: string): Promise<string>; write(p: string, t: string): Promise<void>; stat(p: string): Promise<FsStat> }
export interface EnvPort     { get(name: string): Promise<string | undefined> }
export interface SessionPort { root(): Promise<string>; surfaces(): Promise<readonly RenderSurface[]>; version(): Promise<SessionVersion> }
export interface CommandPort { register(spec: CommandSpec): Promise<void>; run(name: string): Promise<CommandRunResult>; list(): Promise<readonly CommandRow[]> }
export interface UiPort      { open(args: PaneOpenArgs): Promise<UiOpenResult>; close(id: string): Promise<void>; panes(): Promise<readonly UiPane[]>
                               toast(text: string): void; log(to: 'debug', text: string): void; copy(text: string, surface: RenderSurface): Promise<UiCopyResult> }
export type Ports = { process: ProcessPort; state: StatePort; store: StorePort; clock: ClockPort; http: HttpPort
                      fs: FsPort; env: EnvPort; session: SessionPort; command: CommandPort; ui: UiPort }

// What ui/ gets per render: the surface's element table, subscribed reads, and dispatchers. Nothing else.
export type ViewPorts = { el: ElementTable; read: StatePort['read']; act: Actions; props: PaneProps }
export type Actions = { enqueue(job: JobInput): void; kick(): void; setView(fn: (v: View) => View): void; close(): void; copy(text: string): void }
```

```tsx
let runtime: Runtime | undefined                         // module scope: lost on reload, rebuilt below

export const register: Register = (on, options) => {
  on('session.start', async ($, e, next) => {
    runtime?.dispose()
    runtime = createRuntime(portsOf($), options)          // services/runtime.ts: runner, scheduler, probe
    await lifecycle.onSessionStart(runtime, e)            // < 5 ms work; the rest via ports.clock.after(0, …)
    return next(e)
  }).catch((_$, e, next) => next(e))

  on('command.run', { command: 'mods' }, ($, e) => commands.mods(portsOf($), runtime, e))   // returns { text }, never next
    .catch(() => ({ text: 'modmgr failed to answer; run with --debug for the reason.' }))

  on('ui.render', { component: 'Pane', requestId: 'modmgr' }, ($, e) =>
    Pane.render({ el: $.ui.resolve(e), read: statePorts($).read, act: actionsOf(portsOf($), runtime), props: e.props }))
    .catch((_$, e, next) => next(e))

  on('ui.close', { id: 'modmgr' }, ($, e, next) => escCascade(portsOf($), e, next))    // answers without next to keep open
    .catch((_$, e, next) => next(e))

  on('session.append', ($, e, next) => devWatch.observe(portsOf($), e).then(() => next(e)))
    .catch((_$, e, next) => next(e))
}
```

Layering test (vitest, parses imports and source): `domain/` imports `domain/` only; `services/` and `ui/` import
`domain/`, `ports.ts` types and `claude-code` *types* only (no value import of `claude-code` outside `register.tsx`);
the string `$.` appears only in `register.tsx`; in `register.tsx` every function with a `$` parameter is top-level;
no `.catch(` argument mentions `$`; `ui/` imports no `ProcessPort`, `HttpPort` or `FsPort`. The keymap and benchmark
tests are unaffected.

Why this beats the alternatives considered: a single `Ports` object everywhere makes fakes heavy and lets `ui/` reach
`process`; per-noun interfaces keep fakes to the nouns a test needs and give the layering test something to assert.
A `class Services($)` is refused outright (`new S($)`, README:190). Passing `on` to imported registrars is allowed and
tempting, but it scatters the F37 bookkeeping across files; one `on` per event in `register.tsx` is the only place the
"once per module" rule is visible.

## 5. UX implications for the `/mods` dialog

- **Reload**: works from the dialog's buttons and the band (S8 a, c) and never from the `/mods` command itself
  (S8 b, d). So "Apply" must live on a Button, and `/mods apply`-style text subcommands end with "run /reload-plugins
  (or restart) to apply", as PLAN §2.7 says. `$.command.run` "queues until the session is idle" (F7), so an Apply
  pressed during a turn shows "reload queued, runs when the turn ends" rather than a spinner (M12). The resolved text
  ("Reloaded: 1 plugin · …") is worth echoing in the band.
- **Re-attach after a modmgr reload**: F31 keeps the pane open; d.ts:7333-7341 says an open "the plugin makes on its
  own waits undrawn below 144 terminal columns", so C3's "re-attach without reopening" is required, not optional:
  check `$.ui.panes()` and retitle at most.
- **Esc cascade** (M10, MINOR): d.ts:7380-7392: with `closeOnEscape`, Esc also closes the pane "at an idle, empty prompt
  once the prompt has the keys again". Both arrive as `ui.close` with `origin.kind: 'person'`, so the cascade (pop
  overlay, then clear filter, then close) would swallow an Esc typed at the prompt by popping an overlay the person
  cannot see is focused. Decide with `(await ports.ui.panes()).find(p => p.id === 'modmgr')?.isFocused`: cascade only
  while the pane holds the keys, otherwise let the close through. `unload` never reaches the hook (d.ts:7311-7314).
- **`holdToasts`** (M11, MINOR): d.ts:7393-7403 holds every other plugin's toasts while the pane is shown, and the
  doc says it is "for a dialog the person answers and leaves, not a pane that stays". A `/mods` left open on the Job
  log while a 50 s detector pass or a streamed `claude plugin test` runs would silence other mods. Either open without
  `holdToasts` when the Jobs overlay is on top (each open "sets it anew", so re-open the same id to drop it) or keep
  the dialog short-lived and push long jobs to the band.
- **Declared commands** (M9): on the terminal the review screen's `[y confirm]` path works end to end; on the desktop
  app and other SDK hosts it should degrade before the confirm, not after. The pre-confirm re-verify (PLAN §2.3) is
  cheap and side-effect free, since nothing runs before acceptance (S2), and the sha can be checked locally with the
  verified formula before even calling the CLI.
- **Staleness**: `/reload-plugins` does not re-register an unchanged modmgr (F30), so module-memory caches (the
  catalogue index) survive a batch reload and only `$.state` needs the post-reload refresh. The `↻` in the title
  should key off the `list --json` refresh, not off reloads.
- **Degraded modes**: F32 says the engine is always the CLI, so "read-only on desktop" (PLAN §5.2) is too pessimistic
  for process access and too optimistic for declared-command installs; split the degraded flags into `process`
  (probe) and `acceptCommand` (surface-derived).
