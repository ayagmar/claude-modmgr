## 1. Findings

### R-M3a-1 (MAJOR) The draw and the action resolve "selected" differently

Evidence: `plugin/hooks/ui/Pane.tsx:69-70` draws `selected = rows[selectedIndex(rows, view.selected)]`, and
`selectedIndex` (`domain/view.ts:107-110`) falls back to index 0 when `view.selected` is not among the filtered rows.
`services/actions.ts:168-171` resolves `toggle()` from `view.selected` alone, against `mods`, not the filtered rows.

Reproduced: focus `turn-band`, type `red` in the filter (rows = `[redactor]`), press the footer's `e: toggle`. The pane
shows redactor as the selection and the split's detail header for redactor (with "Reading what it can do…" forever,
since nobody called `select(redactor)`), while `stagedChanges` now holds `turn-band`, a row that is not on screen.
"1 staged change" appears with no visible `→ off`. The same gap hits a selection that a refresh removed
(uninstalled elsewhere) and a pane whose ring never landed on a row (focus refused, mouse user on desktop): the footer
draws `toggle` because `selected` fell back to rows[0], but the press does nothing.

Why it matters: PLAN §5.1 "safe by default": a toggle must stage what the person is looking at. The review screen
would show the right command, so nothing wrong runs, but the staged count and the row disagree, and the split's
detail shows a row whose facts never load.

Fix: one resolver in `domain/view.ts`, used by both sides:
```ts
export const selectedRow = (view: View, mods: readonly ModRow[]): ModRow | undefined => {
  const rows = filterRows(mods, view.query)
  return rows.find(row => row.id === view.selected) ?? rows[0]
}
```
`drawPane` uses it for `selected`; `toggle(id?)` uses `id ?? selectedRow(view, mods)?.id`; `focusRow`/`filter`
call `select(selectedRow(...)?.id)` after the write so the split's detail is for the row drawn. Add the repro above
to `test/services/actions.test.ts` and a UI test (filter, then `act:toggle`, expect `→ off` on the visible row).

### R-M3a-2 (MAJOR) `confirm` is not idempotent: two presses queue two batches

Evidence: `services/actions.ts:192-207` reads `review`, calls `queueBatch` (an `enqueue`, a `panes()`, a `ui.open`,
a `kick`), and only then `dropReview()`. Reproduced with `Promise.all([act.confirm(), act.confirm()])`: the queue
holds two `disable turn-band@fixtures` jobs and one reload. The engine delivers a hotkey `y` and an Enter on the
focused confirm as separate presses; the reference says two presses before the redraw both land.

Why it matters: the second disable is a harmless repeat for the CLI, but the Jobs log and the status line say
"2 of 2" for one change, undo inverts a batch of two, and the pattern will not stay harmless for M3b's install/remove.

Fix: take the review by compare-and-set first, then queue what was taken (the versioned `update` serialises the two):
```ts
let taken: ReviewRequest | null = null
await state.update('review', review => { taken = review; return null })
if (taken === null) return
```
If `queueBatch` then fails (`rt` undefined), put it back. `undo` and `reload` are already safe (`undoSpecs` sees the
active batch; `enqueueReload` dedupes); `apply` double-push is absorbed by `pushOverlay`.

### R-M3a-3 (MINOR) A stale staged entry draws as if it still changed something

Evidence: `ui/Installed.tsx:47,77` draws `→ off` whenever `view.staged[row.id] !== undefined`; `ui/Detail.tsx:168,200`
likewise. `stagedChanges` (`view.ts:129-135`) and the footer count ignore an entry equal to the row's state, and
`pruneStaged` runs only from `apply()` with nothing to apply (`actions.ts:184`). After a refresh (`r`, or the
runner's `onSettled`) flips a row under a staged entry (the person disabled it from another terminal), the row shows
`○ … → off  off`, "0 staged", and `s` says "Nothing is staged".

Fix: draw from `stagedChanges` membership (pass a `Set` of changing ids to `List`/`Detail`), and prune in
`refresh()` after `registry.refresh()` resolves, so the view and the count agree.

### R-M3a-4 (MINOR) The status line's fade is dead in practice

Evidence: `Pane.tsx:72` computes `statusOf(queue, frame.now)` with a 10 s fade (`view.ts:293,319`), but nothing
redraws the pane 10 s later: `drawPane` subscribes to `view, mods, detail, queue, review, sync, degraded`
(`Pane.tsx:54-62`), and the only timed write after a batch is the runner's `lastReload` clear on `attention`
(`job-runner.ts:130-139`), which the pane does not read. "✓ 1 change applied, plugins reloaded" stays until the next
unrelated write (an arrow key, a refresh), then vanishes mid-glance.

Fix (pick one): drop `now` and keep the line until the next batch or action (honest, simplest, matches "one line
until the next action" for `notice`); or read `attention` in `drawPane` and set the fade to `RELOAD_ECHO_MS` so the
runner's 8 s clear is the redraw. Either way delete the dead `now` plumbing from `PaneFrame`.

### R-M3a-5 (MINOR) The ring is lost after most stack changes (F46)

Evidence: `ringToSelection` runs after `back`, `cancel`, `confirm` only (`actions.ts:164,206,215`). After `s`
(`apply`, `actions.ts:180-190`) the Button the ring sat on vanishes under the Review; same after `h`/`j`
(`overlay`), after Enter on a row in the stacked layout (`open`: the list is replaced by the detail), and after a tab.
F46: Enter then does nothing until an arrow or Tab. `y`/`n` work as hotkeys, so nothing is blocked, but PLAN §5.1
"keyboard-first: every row and action is a Button… so they take focus and Enter" is not met on the dialog's main
path. `autoFocus` cannot help here (it places only when the site takes the keys, d.ts:1131).

Fix: after each push, `ui.focus(PANE_ID, key)` onto the overlay's safe default, as `edge()` already does for rows
(`actions.ts:265`; "an element not yet drawn is awaited, bounded", d.ts:2520-2522): `act:cancel` for the Review (safe
by default), the first action Button for the detail, `act:help`/`act:jobs` to toggle back out. Catch the deny as now
(F47 in tests).

### R-M3a-6 (MINOR) The F45 cascade cannot tell Esc from the close mark, and depends on a redraw per focus change

Evidence: `register.tsx:191,207,234-238`; `actions.ts:291-312`. Both the Esc key and "the person's close mark or
close key" arrive as `origin.kind: 'person'` (d.ts:7317-7319). With `paneHadKeys` true and a detail or review up, a
click on the frame's close mark (or ctrl+x x) pops the overlay instead of closing: the person asked to close and
got "back". Second, `paneHadKeys` is whatever the *last draw* saw. If the keys leave the pane without a redraw (a
click on the transcript, ctrl+x tab cycling to the band) and the person then types Esc at the prompt, the hook pops an
overlay they cannot see, which is M10 again. The d.ts does not say a change of `isFocused` alone redraws a Pane
(d.ts:10246-10249); F45 assumes it. A third surface (desktop + terminal attached) overwrites the flag from whichever
drew last.

Fix: (1) verify live that losing the keys without a key press redraws the pane; if not, also hook `ui.focus` for the
engine's stops (`element` absent, d.ts:13746-13751) on the pane and clear `paneHadKeys` when the ring leaves. (2) For
the close mark: check live whether `$.ui.panes()` still reports `isFocused: true` at hook time after a mark click (Esc
hands the keys back first, F45; a mouse click may not). If it does, `isFocused === true` at the hook means "mark", and
the cascade should let it close. If the engine cannot tell them apart, document it in C11 and keep the cascade
(Esc is the common path). (3) Key the flag by surface, or only trust draws from the surface that raised the close.

### R-M3a-7 (MINOR) Rows overflow at 64 columns in the worst case

Evidence: `ui/Installed.tsx:12,21-24,76` budgets `FLAGS = 16` cells and marks the flags Box `flexShrink={0}` (F48).
The flags can be `→ off` (5) + `⊘` (1) + `↑` + 12 chars of version (13) + `▲12` (3) + `◆3` (2) + 4 gaps = 28. With
the name at its 26-cell minimum at 64 columns, the row is 49 + 28 = 77 cells: Ink neither wraps nor truncates a
non-shrinking flex row, so the end is cut at the frame or paints over it. Common rows fit; a disabled, locked mod with
an update and problems does not.

Fix: budget the name from the flags actually present (`flagsOf(row)` width), cap `updateTo` at 8 code points in the
row (the detail has the full version), and give the flags Box `overflow="hidden"` with `wrap="truncate-end"` so the
worst case loses the tail of the flags, not the frame.

### R-M3a-8 (MINOR) Stacked detail/overlays are not clipped; the footer scrolls away

Evidence: `Pane.tsx:2-4` says the tree is "sized to `scroll.bodyRows` so the header and footer never scroll away",
but only the split body has `height={listRows} overflow="hidden"` (`Pane.tsx:119`). Stacked, `detailOf(true)` and
the overlays are drawn at full height (`Pane.tsx:131-137`): a mod with many calls and events (the detail lists every
one, C11) exceeds `bodyRows`, the frame scrolls, and the `esc back` / action Buttons sit below the fold; a Jobs
overlay with 12 jobs and five tail lines each is 60+ rows.

Fix: wrap the stacked body in the same clipped Box, and let the overlays window themselves (Jobs already takes
`limit`; the detail can show the first N reach items with "… n more"), or accept scrolling and say so in C11 and the
comment. The 14–24 `rows` request (`view.ts:57`) is moot either way: inline the frame fits the tree up to the room.

## 2. What is right (worth keeping as is)

- **Esc cascade shape** (`view.ts:258-263`, `actions.ts:291-312`): pop → clear query → close, the review dropped on
  pop, `retake` re-opening with `focus` and `holdToasts` only when idle, a plugin close resetting the view. Matches
  M10/C8 and the d.ts manners (d.ts:7355-7381).
- **Toggle → review → batch → reload**: `stageToggle` un-stages on a round trip; `toggleReview` says scope, notable
  facts of what turns on, parts of what turns off, repo-file change, the exact CLI lines (ids charset-validated by
  `parsePluginId` before they can reach argv or `commandLine`); `confirm` clears only the batch's staged ids;
  `queueBatch` re-opens without `holdToasts` (C8); the runner's settle, `reloadPending`, and the 8 s echo work and are
  tested on both surfaces.
- **API use**: `ui.open` manners, `rows`, `holdToasts`, `closeOnEscape` (d.ts:7324-7405); `ui.focus` from a press,
  awaited and bounded (d.ts:2515-2530); `autoFocus` on one row (d.ts:1125-1131); `Input` `value`/`onInput`/`onSubmit`
  signatures; `overflow`/`height`/`columnGap`/`flexShrink` are `BoxProps`; `wrap="truncate-end"` is a Text prop;
  theme keys only (asserted by the layering test); the band returns `undefined → next(e)` under `hasSurvey`;
  `command.run` answering `{}` for a placed dialog is a valid `CommandRunResult` (d.ts:1827-1832).
- **Security**: every name, version, message, tail line, warning and notice is drawn through `sanitize` as `Text`;
  the one unsanitised name (`view.ts:175`, the review's notable line) is safe because `ModRow.name` derives from a
  `PLUGIN_ID`-validated id (`domain/ids.ts:22-23`, `mods.ts:80`). Capability names and explanations come from
  modmgr's own tables, not the mod.
- **Validator**: only the two own-pane gates are allowed; `/mods` still "answers its own command".

## 3. Before M3b (update / remove / undo, capability diff, status line, title badge)

- **Undo must go through the review once removes exist.** `undoSpecs` inverts `remove → install`
  (`domain/jobs.ts:156-171`) with target and scope only; a reinstall of a mod with a declared command would fail as
  `conflict` in the runner (C10), and `z` today queues straight from the Installed footer (`actions.ts:218-228`)
  with no review. Route an undo containing an `install` through the Review (with the re-verified sha) and keep the
  direct path for pure toggles. Decide `--keep-data` there (HANDOFF-M3).
- **Retitling resets the manners.** The title badge (`mods · 2 updates`) is a `ui.open` with the same id, and each
  open "sets anew" `closeOnEscape`, `holdToasts` and `rows` (d.ts:7379-7381, 7390-7395). A badge update from a timer
  must re-send the current manners (hold only when idle) or it silently flips `holdToasts`; an unasked open from a
  timer is also the "waits undrawn below 144 columns" case (d.ts:7328-7332), so retitle only when `panes()` lists the
  pane as placed. Put this in `paneOpen` as the single place that knows the manners.
- **Status line** needs a `status(text | undefined)` method on `UiPort` (`register.tsx:145-154`); it is a `$.ui.status`
  call, one per plugin, cleared with `undefined` (d.ts:2440-2449). Drive it from `bandOf`'s inputs so the band and the
  status line never disagree.
- **Capability diff**: `attention.capsChanged` is already in the band text (`view.ts:360`); Health needs the per-mod
  list and `[x remove] [z undo]`, which lands on the undo point above.
- **Contract hygiene**: `View.layout` and `View.page` are unused (C11); drop them with a `view/3` bump when M3b next
  touches the shape, so the state tag history stays honest.
- **R-M3a-1's resolver** is the foundation for update/remove on "the selected row": fix it first.
